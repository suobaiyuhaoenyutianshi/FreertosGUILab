# Trae 调试控制台 HardFault 取证操作手册

> 面向对象：AI 智能体（或人）要**自己操作** Trae 里的 cortex-debug 会话，
> 通过"调试控制台 + Watch + 调用堆栈"自主完成 HardFault 现场取证，全程不需要用户配合截图。
> 本文由一次真实排障（STM32F103 + FreeRTOS 示波器工程，按键任务崩溃）总结而来。

---

## 0. 一句话流程

**点开"调试控制台"→ 底部出现 `>` 输入行（点击后出现竖线光标）→ 输入 GDB 命令回车 → 读 `$N = 0x...` 输出 → 用地址反查源码行 → 结合调用堆栈和源码定位 bug。**

---

## 1. 界面识别（先说清楚"点哪里"）

Trae 是 VS Code 风格深色界面，调试时默认在底部/侧边有一排面板 Tab：

| 面板名 | 长什么样 | 有什么用 |
|---|---|---|
| **调试控制台 (Debug Console)** | 上方有"筛选器(例如 text、!exclude)"过滤框，主体是 GDB 输出（彩色），**底部有一条 `>` 输入行** | **在这里敲 GDB 命令** |
| **变量 (Variables)** | 树形展开 Local / Global / Registers | 看局部/全局变量、寄存器 |
| **监视 (Watch)** | 空列表，点 `+` 添加表达式 | 添加 `hf_ctx` 后点开三角逐字段看 |
| **Cortex Live Watch** | 常显示 "Use & Enable liveWatch" 提示 | 运行时实时刷新变量（需要 launch.json 配置，非必须） |
| **调用堆栈 (Call Stack)** | 从上到下是当前调用链 | 看崩在哪一层、有没有"未知源 ??@"帧 |
| **断点 (Breakpoints)** | 列出所有断点 | 确认停在哪个断点 |

**输入行的识别标志**：调试控制台最底部有一个 `>`（大于号）。**点击它，输入框出现竖线光标 = 聚焦成功，直接打字即可**，回车后命令发给 GDB，结果以 `$1 = 0x...` 形式打印在面板里。

---

## 2. AI 自主操作步骤（照做即可）

1. **截屏看全局**：先截一张 Trae 窗口，确认上面几个面板的物理位置，决定在哪输入命令。
2. **聚焦调试控制台**：点击底部 `>` 输入行，确认出现竖线光标。
3. **逐条敲命令**：一次敲一条、回车、等输出、记下值，再敲下一条。**不要一次粘贴多条**（输出会混）。
4. **读结果**：`p/x hf_ctx.pc` 这类命令输出形如 `$1 = 0xb29100`，原样记录。
5. **看调用堆栈**：点开 Call Stack 面板，记录每一帧的名字和地址，特别注意 `??`（未知源）帧——那往往是跑飞/野指针跳到的地址。
6. **反查源码行**：拿到地址后，回本地用 addr2line 映射（见 §4.4）。

## 3. GDB 常用命令清单（直接可用）

### 3.1 看全局变量（最常用）

工程在 `stm32f1xx_it.c` 里定义了现场容器 `hf_ctx`（结构体，一次装完全部现场），硬故障时 `hardfault_dump()` 自动填好。**看一个容器 = 拿全部现场：**

| 命令 | 作用 |
|---|---|
| `p hf_ctx` | **一行打印全部 13 个字段 + 任务名**（最推荐） |
| `p/x hf_ctx` | 全部字段按十六进制打印 |
| `p/x hf_ctx.cfsr` | 单看某个字段 |
| `p/x hf_ctx.task_name` + `x/s hf_ctx.task_name` | 看崩溃任务名 |
| `x/16xw &hf_ctx` | 按内存原始字看 16 个字 |

字段含义（跟硬故障取证一一对应）：

| 字段 | 含义 |
|---|---|
| `hf_ctx.r0~r3` | 函数前 4 个参数；**非法地址常躺在 r3** |
| `hf_ctx.pc` | 现场指令地址（出事时正在执行哪条）→ 反查源码行 |
| `hf_ctx.lr` | 返回地址 → "谁调用进来的" |
| `hf_ctx.exc_return` | `0xFFFFFFFD`=崩在任务(PSP)；`0xFFFFFFF9`=崩在中断(MSP) |
| `hf_ctx.hfsr` | bit30 FORCED=1 说明是下级 fault 升级成的 HardFault |
| `hf_ctx.cfsr` | **真正故障原因**：IBUSERR/PRECISERR/IMPRECISERR/UNALIGNED/INVSTATE... |
| `hf_ctx.bfar` | 出错访问的数据地址（仅 CFSR bit15 BFARVALID=1 才有效） |
| `hf_ctx.mmfar` | MemManage 坏地址（CFSR 低 8 位非 0 时看，不看 BFAR） |
| `hf_ctx.sp` | 出事时的栈指针，事后 `x/32xw hf_ctx.sp` 走栈用 |
| `hf_ctx.cur_task` / `task_name` | 崩溃任务句柄 / 任务名 |

> 注意：`hf_pc`、`hf_cfsr` 等旧名字现在只是宏别名（`#define hf_cfsr hf_ctx.cfsr`），**GDB 里不认宏**。
> 在 GDB / Watch 里一律用 `hf_ctx` 或 `hf_ctx.xxx`，不要用旧的 `hf_pc`。

### 3.2 看 CPU 寄存器

```
info registers        # 全部寄存器（r0~r15, sp, lr, pc, xpsr, msp, psp）
info reg psp          # 单独看某个
p/x $pc
p/x $lr
```

注意：停在 `hardfault_dump` 时，`$pc` 是 dump 函数的地址（0x08004e44 之类），**不是**出事指令；
真正出事的 PC/LR 在 `hf_ctx.pc` / `hf_ctx.lr` 里。

### 3.3 看栈内存

```
x/32xw hf_ctx.sp      # 从出事栈指针往下看 32 个字，走异常帧/回溯
x/8xw 0x20004bb8      # 直接看绝对地址
```

FreeRTOS 栈填充是 `0xa5a5a5a5` —— 看到一大片 0xa5a5a5a5 说明那块内存从未被使用过，
若函数指针/局部变量读出来是 0xa5a5a5a5，说明读到了"从没写过"的垃圾栈。

### 3.4 地址反查源码行（在终端跑，不在 GDB 里）

```
arm-none-eabi-addr2line -e build/Debug/FreertosGUILab.elf -f 0x0800b567
# 输出：vKeyWorkerTask / key/keyTask.c:25
```

技巧：
- `hf_ctx.pc` → 出事指令的源码行
- `hf_ctx.lr` → 谁调用进来的源码行（**这个往往更接近根因**）
- 地址 `0x0800xxxx` = Flash 指令区（合法）；`0x00xxxxxx`、`0x2xxx` 等在 Flash 外的 = 野指针/跑飞

## 4. 取证逻辑链（hardfault-forensics 8 步，压成 5 步）

1. **看 HFSR**：`p/x hf_ctx.hfsr`。FORCED=1 → 真凶在 CFSR，继续。
2. **看 CFSR 判类型**：`p/x hf_ctx.cfsr`
   - `0x100` = **IBUSERR**（取指总线错误，PC 跳飞了）→ 查 pc 和调用来源
   - bit9 PRECISERR + bit15 BFARVALID → PC 可信 + BFAR 有效，双锁定
   - bit10 IMPRECISERR → PC 漂移，现场 ≠ 肇事时刻，靠 lr 重建调用链
   - bit12 STKERR → 栈坏了，查任务栈大小/数组越界
3. **判崩在哪**：`p/x hf_ctx.exc_return`。0xFFFFFFFD→任务(PSP)；0xFFFFFFF9→中断(MSP)。
4. **反查源码**：`hf_ctx.pc` + `hf_ctx.lr` → addr2line。
5. **收尾问"暴露点 vs 暴源"**：崩的位置 ≠ 坏的位置。地址合法 ≠ 不是它的错。
   用调用链 + 崩溃任务 + 现场寄存器，找**最早写坏那块内存的函数**。

## 5. 实战案例复盘（本次真实排障）

**现象**：按一次按键，程序 HardFault，停在 `hardfault_dump` 的 `while(1)`。

**取证过程（全部 AI 自操作）**：

```
p/x hf_ctx.hfsr   → 0x40000000   (FORCED=1)
p/x hf_ctx.cfsr   → 0x100        (IBUSERR：取指总线错误)
p/x hf_ctx.pc     → 0xb29100     (非法地址，不在 Flash 0x0800xxxx)
p/x hf_ctx.lr     → 0x0800b567   (返回地址)
p/x hf_ctx.r3     → 0xb29100     (同一个非法地址，函数指针被踩)
p/x hf_ctx.exc_return → 0xfffffff9 (崩在任务上下文)
p/x hf_ctx.r12    → 0xa5a5a5a5   (FreeRTOS 栈填充！函数指针从垃圾内存读出)
```

调用堆栈面板：`hardfault_dump → <signal handler> → ??@0x00b29100 → vKeyWorkerTask@0x0800b566`

addr2line：`hf_ctx.lr` → `key/keyTask.c:25`（`vKeyWorkerTask` 的 `job.xfu(job.arg)` 调用）。

**结论**：`vKeyWorkerTask` 里 `job.xfu(job.arg)` 调用了野函数指针 `0xb29100` → BLX 取指失败 → IBUSERR。
根因是发送端 `vkeyOneSca()` 把事件打包成"首字节路由号 + job 右移 1 字节"入队，而接收端按原始 `job_t` 直接收，
导致 `job.xfu` 错位成垃圾值。现场数据（r3/pc 同地址 + r12=栈填充）与静态代码分析完全闭环。

**取证时读变量 vs 读屏幕的经验**：
- 变量是全局的，**直接敲 `p/x hf_ctx.xxx` 比看屏幕截图快**；
- 调用堆栈面板可以不用截图，用 `bt` 命令看（但 cortex-debug 下 Call Stack 面板更直观）；
- 每条命令之间等输出再敲下一条，避免 `$N` 编号对不上。

## 6. 注意事项（安全红线）

1. **绝不点"继续 / 复位 / 重启 / 单步"按钮**——会毁掉现场。只读命令（p / x / info）永远安全。
2. 在 `hardfault_dump` 的 `while(1)` 里读 `hf_*`/`hf_ctx`，读的是 RAM，不会二次崩溃。
3. 不要在 GDB 里调 printf 相关函数（可能再次崩）。
4. 读 CFSR 不会清零（写 1 才清），放心读；但**第一次读到的值最珍贵**，先记下来。
5. GDB 不认 `#define` 宏别名（如 `hf_pc`），一律用 `hf_ctx.xxx`。
6. `hf_ctx` 是普通全局变量，调度器没起来前 `cur_task`=0、`task_name`=NULL，属正常。
7. 项目里 `Core/Src/stm32f1xx_it.c` 和 `DmmAndGui/stm32f1xx_it.c` 是两份相同副本，
   目前只有 Core/Src 参与链接；**重新 configure 后两份都会进构建 → 重复符号链接报错**（历史遗留，建议后续删一份）。

## 7. 给"写技能"的人的建议清单

一个自动取证技能至少应包含：
1. **UI 操作**：定位调试控制台 `>` 输入行、点击聚焦、逐条输入命令、截图/读输出。
2. **命令集**：§3 的命令表（尤其 `p hf_ctx` 一次拿全部）。
3. **判读规则**：§4 的 CFSR 分类 + EXC_RETURN 判定 + addr2line 反查。
4. **安全约束**：§6 的红线。
5. **案例库**：把 §5 这类真实案例存下来当 few-shot。
