## 二、分题答案要点

### 第 1 题 · 基础概念(队列)

**题干**:生产者 `vKeyWOrksScan` 每 10ms 扫 6 个键发 `job_t` 进容量 10 的 `xKeysQue`;消费者 `xQueueReceive(..., portMAX_DELAY)` 死等。

**关键错的点:主语(生产/消费)说反过。**

- 队列靠**临界区(关中断/挂调度器)** 保证出入队操作原子,不会自相矛盾。
- **队列满直接影响的是生产者**(不是接收端):
  - `xQueueSend(...,0)` = 满则**不阻塞、立即返回 `pdFAIL`、消息丢弃**(按键场景可按丢就丢)
  - `>0` = 阻塞等空位、超时仍失败
  - `portMAX_DELAY` = 一直等,直到有空位(生产者)
- 消费者用 `portMAX_DELAY` 死等不会卡死系统:消费者**阻塞挂起**,不占 CPU,等队列有数据/通知唤醒。
- 本处是**单生产者**(同一扫描任务内串行发),天然不会"同时",但这只是特例不是通用保证。

> 项目隐患:代码里 `xQueueSend(...,0)` 的返回值被忽略,队列满事件静默丢 → 按键"按了没反应"。

### 第 2 题 · 机制加深(回调与栈)

- 回调 `job.xfu(job.arg)` 运行在**消费者任务 `vKeyWorkerTask` 的栈**上。
- 在回调里开大局部数组 → **写穿这块任务栈的边界 → 破坏紧邻的那块内存(通常是别的任务/TCB)**,"一路滚进堆"说法不严谨。用内存监视任务/`uxTaskGetStackHighWaterMark()` 核;崩了查 GDB `bt` / PC/LR/Cortex-M 寄存器。
- **最隐蔽的饿死根因**:慢回调霸占消费者 → 队列消费不过来 → **满** → 后到的兄弟按键因发送被**静默丢弃**。这不是单点饿死,而是整条队列被拖垮。
- 项目里 [key.c#L21-L23](file:///c:/Users/zhouhaoen/OneDrive/Desktop/FreertosGUILab/key/key.c#L21-L23) 用 `xSemaphoreGive(key->xSem)` 把慢回调**改由另一个专职任务**执行,把慢活从消费者摘出去 —— 这是"解耦慢事件"的正确解法。

### 第 3 题 · 异常处理(HardFault + 钩子)

**A. HardFault 现场翻译**:`hf_pc=0x0800_0042`(Flash 代码区,出错的那条指令)、`hf_bfar=0x2000_1F4C`(RAM/SRAM,指令正在读写的坏地址)。合起来:"正在执行 Flash 指令 0x08000042,精确地非法读写 RAM 0x20001F4C"。要先看 **CFSR**(`PRECISERR`/`BFARVALID`)判断 PC/BFAR 是否可信,否则去反汇编/`.map`;`hf_exc_return` 判断崩在任务(PSP)还是中断(MSP)。

**B. 两个兜底钩子**(此前完全空着,**背熟**):

| 钩子 | 触发时机 | 判断标准 |
|---|---|---|
| `vApplicationStackOverflowHook()` | 栈溢出被判定的瞬间 | 需开 `configCHECK_FOR_STACK_OVERFLOW=1/2`,且**上下文切换时**才查 |
| `vApplicationIdleHook()` | 空闲任务每次运行 | 常年喂软件看门狗;需开 `configUSE_IDLE_HOOK=1`,"空闲任务还被调度到=系统没被死循环卡死" |

> 钩子必须在 `FreeRTOSConfig.h` 打开对应宏才生效,否则写了不执行。

### 第 4 题 · 架构扩展(新高频源)

- 复用按键队列的**三个问题**:① 信息丢失(高频覆盖/满丢弃)② 时效性差/耦合 ③ **数据语义与速率不同**(一次性按键 vs 连续流混进同一队列,消费者成瓶颈)。
- 改法:**独立队列 + 独立消费者**。判据:**数据是否同源、速率是否同量级**,同才考虑复用。
- "只要最新、丢中间帧" → FreeRTOS 里是 **长度=1 的队列 + `xQueueOverwrite()`(覆盖式写)**,或 **任务通知 + 共享双缓冲**。这些**不是** mailbox、也不是广播。
- 概念纠正:**FreeRTOS 没有内置 mailbox 广播;广播是事件组(Event Group)** 多路 bit 唤醒多任务。别把概念串了。

### 第 5 题 · 综合判断

| 场景 | 本项目原语 | 正确选型 |
|---|---|---|
| 按键快回调 | 队列 `xKeysQue` | 队列(偶发事件) |
| 按键慢回调 | 信号量 `key->xSem` | 信号量通知专职任务 |
| 采满一帧 | 任务通知 + 双缓冲 | 通知 + 双缓冲(只要最新) |
| LCD 重绘 | 事件组 `xEventLcd` | 事件组(广播多路) |

- **优先级反转**:会出现在"低优任务持有资源、高优任务被它挡"。落到本项目:慢回调专职任务(或长消费者)拿到资源 → 高优示波器任务被压。别光说"互斥锁"。
- **"所有回调统一压进队列"是倒退**:快慢回调同队列同消费者 → **高优按键被慢回调拖累并发出实时性**(反转雏形)。现做法(单独信号量路)是对的。

## 三、高频"主语错记榜"

1. ~~队列满影响接收~~ → **影响生产者**。
2. ~~栈溢出滚进堆~~ → **破坏相邻内存**(别的任务/TCB)。
3. ~~FreeRTOS 有 mailbox/广播~~ → 覆盖式**队列/任务通知** + 事件组**广播**。
4. ~~回调跑哪不清楚~~ → **跑在触发它的那个消费者/调用者任务栈上**。

## 四、真实市场调研(实习岗真实标准)

- **C 语言占比重最高**(volatile/static/指针/宏/大端小端/内存分区),几乎每家必问。
- **单片机集中:中断 + 通信接口**(IIC/SPI/UART),以及项目里 GPIO/中断/定时器怎么用。
- **RTOS 是必考但通常在二三轮**,话题即本次模拟的高频:队列、二值信号量 vs 互斥锁、优先级反转/继承、上下文切换、任务栈/溢出、`*_FromISR`。
- 我出的题"话题全对、难度比平均高":把陷阱和术语精确度拧得比真实实习面试更狠。

**结论**:实习面试不是"考满分才进"。**基础 C 清楚 + 单片机常用 + 一个真硬件项目 + RTOS 能说个所以然**即可过。你有真项目(FreeRTOS 平衡车 + ADC/DMA 示波器 + DAC 信号发生器),是最大加分项。
