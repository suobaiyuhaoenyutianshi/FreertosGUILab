## F01 调度器切换 / PendSV / PSP

### 一句话答案

FreeRTOS 在 Cortex-M3 上把“启动第一个任务”和“任务切换”拆成两条异常路径：**SVC 负责第一次进任务并设置 PSP，PendSV 负责后续每次切换**；任务跑在 PSP 上，中断跑在 MSP 上，所以切换任务本质上只是换一个 PSP 和一组 TCB。

### 原理链（5 步）

1. `main()` 调用 `vTaskStartScheduler()`，最终进 `xPortStartScheduler()`。
2. `prvPortStartFirstTask()` 先做一件很多人答不出的细节：从向量表把 MSP 重置到栈顶。
   - 读 `0xE000ED08`（VTOR）→ 取向量表基址 → 取 `[0]` 初始 MSP → `msr msp, r0`。
   - 然后 `cpsie i/f` 开中断，再 `svc 0` 触发 SVC。
3. `vPortSVCHandler` 从 `pxCurrentTCB` 取出当前任务栈顶：
   - `ldmia r0!, {r4-r11}` 恢复软件保存的 8 个寄存器；
   - `msr psp, r0` 把剩下的栈指针写进 PSP；
   - `mov r0,#0; msr basepri,r0` 开中断；
   - `orr r14,#0xd; bx r14`，让 EXC_RETURN 变成 `0xFFFFFFFD` → 异常返回到**线程模式 + 使用 PSP**。
4. 运行期每次 SysTick，`xPortSysTickHandler` 调 `xTaskIncrementTick()`；需要切换时写 `ICSR` 的 PendSV 置位位（`portNVIC_INT_CTRL_REG = portNVIC_PENDSVSET_BIT`）。
5. `xPortPendSVHandler` 完成真正的上下文切换：
   - `mrs r0, psp` 拿到当前任务栈指针；
   - `stmdb r0!, {r4-r11}` 压入硬件**不会**自动保存的 8 个寄存器；
   - `str r0, [r2]` 把新栈顶写回 TCB 第一个成员 `pxTopOfStack`；
   - `bl vTaskSwitchContext` 选下一个任务；
   - 从新 TCB 取栈顶 → `ldmia r0!, {r4-r11}` → `msr psp, r0` → `bx r14`。

### 关键区分：硬件压 8 个，软件压 8 个

进异常时硬件自动压栈的 8 个字（低地址在前）：

| 偏移 | 寄存器 |
|---|---|
| +0x00 | R0 |
| +0x04 | R1 |
| +0x08 | R2 |
| +0x0C | R3 |
| +0x10 | R12 |
| +0x14 | LR |
| +0x18 | PC |
| +0x1C | xPSR |

PendSV 里软件补压的是 **R4~R11**，因为 AAPCS 规定 R4-R11 由被调用者保存，硬件异常入栈不负责它们。

**面试常问“一个任务栈里到底存了什么”**：任务栈 = 硬件异常帧（8 字）+ 软件保存的 R4-R11（8 字）+ 函数调用栈 + 局部变量 + 浮点上下文（如果开了 FPU 且用了浮点）。

### 项目证据

- 启动第一个任务：`freeRTOS/Src/port.c:248-260` 的 `prvPortStartFirstTask()`，`ldr r0,=0xE000ED08` 这三行就是“从向量表重置 MSP”。
- SVC 设 PSP：`port.c:228-245`。
- PendSV 保存/恢复：`port.c:456-490`。
- SysTick 挂 PendSV：`port.c:493-515`。
- 处理函数映射：`freeRTOS/Inc/FreeRTOSConfig.h:627-629`
  ```c
  #define vPortSVCHandler     SVC_Handler
  #define xPortPendSVHandler  PendSV_Handler
  #define xPortSysTickHandler SysTick_Handler
  ```
  这三行把 FreeRTOS 的汇编处理函数“改名”成启动文件里的弱符号，链接时覆盖默认 `Default_Handler`。
- 向量表位置：`startup_stm32f103xb.s:129-146`，第 142 行 `SVC_Handler`、第 145 行 `PendSV_Handler`、第 146 行 `SysTick_Handler`。
- PendSV/SysTick 优先级：`port.c:55-57`，`portMIN_INTERRUPT_PRIORITY = 255`，即两者都配成最低优先级。

### 追问与答法

**Q：为什么 PendSV 必须最低优先级？**
因为 PendSV 是“延迟切换”：SysTick 只负责置位，真正切换要等所有中断都处理完。如果 PendSV 优先级高，它可能打断一个正在用临界区访问内核数据的中断，导致内核数据结构被破坏；最低优先级保证它永远最后执行，且可以被任何中断抢占。

**Q：为什么第一个任务用 SVC 启动，不直接跳过去？**
因为任务必须运行在**线程模式 + PSP**。复位后 CPU 在 Handler 模式 + MSP，只有通过异常返回并构造 `EXC_RETURN=0xFFFFFFFD`，硬件才会自动切到线程模式并改用 PSP。SVC 就是构造这次“异常返回”的入口。

**Q：PSP 什么时候被赋值？**
第一次是 `vPortSVCHandler` 里 `msr psp, r0`；之后每次切换是 PendSV 恢复新任务时再 `msr psp, r0`。中断里不碰 PSP，中断用 MSP。

### 翻车点

- 把“硬件自动压 8 个”和“PendSV 压 8 个”说成同一组寄存器。
- 把 `0xFFFFFFF9` 和 `0xFFFFFFFD` 记反：**F9 = Handler/MSP，FD = Thread/PSP**。
- 说“任务切换时把整个栈拷贝过去”——不是拷贝，是换 PSP 指针。

### 30 秒口述骨架

`启动 SVC → 设 PSP → 线程模式 → SysTick 置 PendSV → 压 R4-R11 → 存 TCB → 选下一个 → 恢复 → bx lr`

## F03 任务栈怎么算（384 字那条）

### 一句话答案

`xTaskCreate` 的第四个参数单位是**字（word）不是字节**，STM32 上 1 字 = 4B，所以 `384` = **1536 字节**；这个值不是拍脑袋，而是“按调用链估算 → 跑起来看高水位 → 留 20%~30% 余量 → 上线后持续监控”的闭环结果。

### 原理链（4 步）

1. **先算谁会吃栈**：局部数组、`printf/sscanf/vsnprintf` 家族、浮点三角函数（`qsin/qcos/qatan`）、深调用链、以及中断嵌套（中断吃 MSP，不吃任务栈，但中断里调用的函数仍可能很深）。
2. **估算**：控制任务 `App_Control_Task` 里有 4 个 `PID_Compute1`、`qatan/qsin/qcos`、`Attitude_t` 结构体、`App_Bat_Pro`，浮点库和三角函数是主要开销，给 384 字（1536B）属于“偏宽裕”。
3. **实测**：`uxTaskGetStackHighWaterMark(handle)` 返回历史最小剩余**字**数；项目里 `memory_monitor.c:87-92` 每 2 秒打印一次，单位换算成字节再乘 4。
4. **留余量 + 监控**：一般保留 20%~30%；本项目还开了 `configCHECK_FOR_STACK_OVERFLOW=2`（栈尾填 `0xA5` 图案，切换时检查被踩），爆栈进 `vApplicationStackOverflowHook`（`main.c:769-783`），只写全局变量 + 关中断死循环。

### 项目里的真实数字

- 控制任务：`main.c:214`
  ```c
  xTaskCreate(App_Control_Task, "ctrl", 384, NULL, 4, &ctrl);
  ```
  384 字 = 1536B。
- 姿态任务：`main.c:218`，256 字 = 1024B。
- 电机任务：`main.c:220`，128 字 = 512B。
- 遥控任务：`main.c:226`，512 字 = 2048B（原 256 字，爆过栈后加倍）。
- UART2 发送任务：`app_usart2_dma.c:132`，128 字。
- MemMon：`memory_monitor.h:17`，256 字。

### 爆栈案例（必须会讲）

`docs/调试记录_蓝牙USART3接收与爆栈复位.md:32-37` 记录了真实事故：

- rc 任务原来 256 字（1KB），里面跑 newlib 的 `sscanf` + `vsnprintf`；
- 一收蓝牙数据就爆栈 → `vApplicationStackOverflowHook` 关中断死循环 → 唯一喂狗的 MemMon 也停了 → IWDG 0.41s 复位；
- 现象伪装成“串口收不到、计数停在 23/2、日志乱码”，实际是 CPU 在反复重启；
- 修复：手写整数解析替代 `sscanf`、`App_USART2_SendRaw` 替代 `vsnprintf`，栈加到 512 字。

**这段的价值**：面试官问“你怎么知道栈不够”，你答“高水位 + 爆栈钩子计数 + 复位日志”，比背“给大一点”强得多。

### 堆与栈的关系（容易混）

- 任务栈、TCB、队列、信号量都从 FreeRTOS 堆（`heap_4`）里分配，`configTOTAL_HEAP_SIZE = 9728`（`FreeRTOSConfig.h:297`）。
- 加大任务栈必须同步加大堆，否则 `pvPortMalloc` 返回 NULL，`xTaskCreate` 失败。
- 全局变量/静态变量在 `.bss/.data`，不在任务栈里；`static` 局部变量也不在栈上。

### 追问与答法

**Q：384 字够不够，你怎么验证？**
看 `uxTaskGetStackHighWaterMark` 的最小剩余；再人为加打印/加滤波跑一遍；上线后用 MemMon 周期性打印，剩余低于 25% 就加。

**Q：`configCHECK_FOR_STACK_OVERFLOW=2` 原理？**
任务创建时把栈末尾若干字节填成 `0xA5`，每次任务切换出去时检查这几个字节是否还是 `0xA5`；被改写就调钩子。方式 1 只检查 SP 是否越界，快但漏检；方式 2 更慢但能抓到大多数。

**Q：中断会不会把任务栈撑爆？**
不会直接用任务栈。Cortex-M 进中断用 MSP，任务用 PSP；但中断处理函数自己的调用链会吃 MSP，MSP 的余量要看启动文件里的栈大小和最深中断嵌套。

### 翻车点

- 把 384 说成 384 字节（实际 1536B）。
- 把“堆不够”说成“栈溢出”（`xTaskCreate` 返回 `errCOULD_NOT_ALLOCATE_REQUIRED_MEMORY` 是堆；高水位见底才是栈）。
- 以为 `static` 局部变量在栈上。

### 30 秒口述骨架

`字×4=字节 → 384=1536B → 浮点/三角函数吃栈 → 高水位实测 → 留 30% → 爆栈钩子 + 堆同步加大`

### 工作区补充：栈深度集中定义 + 百分比监控

`FreertosGUILab` 把栈深度做成宏，创建任务与注册监控共用同一个值（`Core/Src/main.c:55-64`）：

| 任务 | 栈深度（字） | 位置 |
|---|---|---|
| KEYINITSCAN | 128 | `main.c:58,265` |
| KEYIWORK | 128 | `main.c:59,266` |
| led1 | 128 | `main.c:60,273` |
| LCD | 256 | `main.c:61,274` |
| UART1_TX | 256 | `main.c:63`、`app_usart1_dma.c:112` |
| KEYSLOW | 128 | `key/keyTask.h:7,272` |
| float_archIT | 128 | `DmmAndGui/waveFormCapture.h:10,75` |
| MemMon | 256 | `Core/Inc/memory_monitor.h:14` |

监控不仅打印剩余字/字节，还算百分比（`memory_monitor.c:87-96`）：

```c
unsigned uPercent = (uxFreeWords * 100u) / uxTotalWords;
const char* pcFlag = (uPercent <= MONITOR_LOW_STACK_PERCENT) ? "  <-- 余量偏低，考虑扩栈" : "";
```

`MONITOR_LOW_STACK_PERCENT = 20`。这比只打印绝对剩余更好：128 字的任务剩 30 字是 23%，256 字的任务剩 30 字只有 12%，百分比才能横向比较。

面试可直接说：“我两个项目都用高水位，但示波器项目把申请值也注册进去，直接算剩余百分比，低于 20% 打标记。”

## F05 vTaskDelay vs vTaskDelayUntil

### 一句话答案

`vTaskDelay(n)` 是**相对延迟**：从“调用这一刻”起睡 n 个 tick，任务自身执行时间会叠加进周期，长期会漂移；`vTaskDelayUntil(&last, n)` 是**绝对延迟**：按“上一次唤醒时刻 + n”计算，能把执行时间补偿掉，所以周期任务必须用它。

### 原理链（3 步）

1. `vTaskDelay` 把当前任务挂到延迟列表，唤醒时刻 = `now + n`。下一轮再调用时，`now` 已经包含了本轮执行时间，所以真实周期 = 执行时间 + n，误差逐轮累积。
2. `vTaskDelayUntil` 记录 `last_wake`，每次唤醒后把 `last_wake += n`，再睡到新的 `last_wake`。只要执行时间 < n，周期严格等于 n。
3. 如果执行时间 > n，`vTaskDelayUntil` 不会“补跑”错过的周期，而是立即返回（`last_wake` 仍按 n 递增），表现为连续执行几次；这时要检查是不是周期给太紧或任务被更高优先级长期抢占。

### 项目证据

- 姿态任务严格 5ms：`app_mpu6050.c:191` 初始化 `last_wake = xTaskGetTickCount()`，`:231` 用 `vTaskDelayUntil(&last_wake, pdMS_TO_TICKS(5))`。
  为什么必须严格：互补滤波里 `0.005 * gz` 把陀螺仪角速度积分成角度，周期一变，积分系数就错。
- MemMon 用相对延迟：`memory_monitor.c:106` `vTaskDelay(pdMS_TO_TICKS(100))`。
  它只负责“每 100ms 喂狗 + 每 2s 打印”，不要求严格周期，漂移几毫秒无所谓。
- 控制任务已经不用 Delay：`app_control.c:225` 用 `ulTaskNotifyTake(pdTRUE, portMAX_DELAY)`，周期由姿态任务的通知驱动——这是比 `vTaskDelayUntil` 更彻底的事件驱动。
- 电量指示 `App_Bat_Pro()` 用软件节流：`app_bat.c:37-41` 的 `PERIODIC(20)` 宏（`sched.h:6-10`），靠 `HAL_GetTick()` 差值判断 20ms，不是 RTOS 延迟。

### 三种周期写法怎么选

| 场景 | 写法 | 原因 |
|---|---|---|
| 严格等周期采样/控制 | `vTaskDelayUntil` | 补偿执行时间，不漂移 |
| 低频后台/监控 | `vTaskDelay` | 简单，漂移无所谓 |
| 由事件触发（有新数据才算） | 任务通知/信号量阻塞 | 不空转，相位由生产者决定 |
| 裸机遗留逻辑塞进任务 | `PERIODIC(ms)` 宏 | 复用 `HAL_GetTick`，但要保证任务本身被及时调度 |

### 追问与答法

**Q：`vTaskDelayUntil` 的 `last_wake` 为什么要先初始化？**
不初始化时它是 0 或随机值，第一次调用会按“0 + n”算，可能立即返回或长时间不返回。标准写法是任务开头 `TickType_t last = xTaskGetTickCount();`。

**Q：任务执行时间超过周期会怎样？**
`vTaskDelayUntil` 立即返回，连续跑；`vTaskDelay` 则周期被拉长。两种都不是“自动补救”，要靠优先级/周期设计解决。

**Q：`vTaskDelay(1)` 一定是 1ms 吗？**
不一定。它至少延迟 1 个 tick，实际唤醒还受 tick 对齐和更高优先级任务影响；`configTICK_RATE_HZ=1000` 时 1 tick = 1ms，但调度延迟可能让实际间隔更长。

### 翻车点

- 说“两个都是延时，没区别”。
- 说“`vTaskDelayUntil` 会补齐错过的周期”——不会补跑，只是不累积漂移。
- 把 `pdMS_TO_TICKS(5)` 当成 5 个 tick 直接写 5（tick 频率变了就错）。

### 30 秒口述骨架

`Delay=相对会漂 → Until=绝对不漂 → 5ms 采样用 Until → 事件驱动用通知 → 超周期立即返回`

### 工作区补充：什么时候不用 vTaskDelayUntil

`FreertosGUILab` 里几乎没有 `vTaskDelayUntil`，原因不是不会用，而是**采样周期由硬件定时器保证**：

- TIM3 TRGO 触发 ADC + DMA，每 1024 点一帧，周期由 PSC/ARR 决定，不靠任务延时；
- 浮点换算任务用不上 Until，它直接 `ulTaskNotifyTake(pdTRUE, portMAX_DELAY)` 等 ADC 完成通知（`waveFormCapture.c:161`）；
- 按键扫描用 `vTaskDelay(10)`（`keyTask.c:80`），10ms 只是“人手感觉不到”的扫描节奏，不要求严格；
- LED 闪烁用 `vTaskDelay(500/1000)`（`main.c:189-192`），更不需要精确。

结论：**周期精度要求来自业务**。控制环/姿态采样这种“积分步长”必须 Until 或硬件触发；按键、LED、监控用 Delay 就够。面试别把“周期任务一律 Until”背成教条。

## F06 事件驱动改造（邮箱 + 通知）

### 一句话答案

姿态数据用**长度 1 的覆盖邮箱**（`xQueueOverwrite` 写、`xQueuePeek` 读）保证“永远只有最新一份、多读者不消费”；再用**任务通知**（`xTaskNotifyGive` / `ulTaskNotifyTake`）把“有新帧”这件事告诉控制任务，控制任务从“5ms 轮询碰运气”变成“被唤醒后必读最新帧”。

### 改造前的问题

改造前控制任务和姿态任务都是 5ms 周期，控制任务用 `xQueuePeek` 读邮箱：

- 两个任务同周期，谁先跑取决于优先级和相位；
- 控制任务优先级 4、姿态任务 3，控制任务可能先跑，读到的还是**上一轮**姿态；
- 这不是数据损坏，是**相位不确定性**：控制环永远慢半拍，且慢多少不固定。

### 改造后的链路

1. 姿态任务 `App_Attitude_Task`（`app_mpu6050.c:189-233`）：
   - 读 MPU6050 → 互补滤波 → 组装 `Attitude_t`（含 `tick` 时间戳）；
   - `xQueueOverwrite(x_at_T, &a)` 覆盖邮箱（长度 1，永远成功、不阻塞）；
   - `xTaskNotifyGive(ctrl_h)` 通知控制任务；
   - `vTaskDelayUntil` 保证 5ms 采样周期。
2. 控制任务 `App_Control_Task`（`app_control.c:217-231`）：
   - `ulTaskNotifyTake(pdTRUE, portMAX_DELAY)` 阻塞等通知；
   - `pdTRUE` 表示“取走时把计数清零”，避免姿态任务连发多次、控制任务只醒来一次却以为只来了一帧；
   - 醒来后 `App_Control_Proc()` 里 `App_MPU6050_GetAttitude()` 用 `xQueuePeek(..., 0)` 读最新快照。
3. 初始化顺序（`main.c:212-218`）：
   - 必须先创建控制任务拿到 `ctrl` 句柄，再把 `ctrl` 作为参数传给姿态任务；
   - 否则姿态任务拿不到通知目标。
4. 首帧问题：`ulTaskNotifyTake` 一开始会阻塞，直到姿态任务跑完第一轮；`main.c` 注释里说“初值给 1 保证先跑一帧”，实际代码没显式给，靠姿态任务 5ms 后自然通知——面试时要说清“首帧最多晚 5ms，控制环此时本来也没有有效姿态”。

### 三种通信语义对照（面试最加分）

| 机制 | 写端 | 读端 | 语义 | 项目位置 |
|---|---|---|---|---|
| 覆盖邮箱 | `xQueueOverwrite`，满也覆盖、恒 `pdPASS` | `xQueuePeek`，读不移除 | 只保留最新状态，多读者可反复看 | 姿态 `xQueueCreate(1,sizeof(Attitude_t))` |
| 普通队列 | `xQueueSend`，满则阻塞/失败 | `xQueueReceive`，读即消费 | 每条消息都要处理，不能丢 | UART2 打印队列 `app_usart2_dma.c:123` |
| 二值信号量 | `xSemaphoreGiveFromISR` | `xSemaphoreTake` | “有事件”计数（最多 1） | 蓝牙整帧 `app_rc.c:24,85,105` |
| 任务通知 | `xTaskNotifyGive` / `...FromISR` | `ulTaskNotifyTake` | 最轻量，直接写目标 TCB，一对一 | 姿态→控制 `app_mpu6050.c:227` |

**为什么姿态不用普通队列**：控制环只关心“现在是什么姿态”，不关心历史；队列满时写端要么阻塞（拖乱 5ms 采样）要么丢帧，都不如覆盖。
**为什么蓝牙用信号量而不是邮箱**：每条遥控命令都要执行，不能只留最后一条。
**为什么用通知而不是再建一个信号量**：通知不需要额外分配队列对象，速度快、省堆；缺点是只能一对一，不能多任务等同一个通知。

### 追问与答法

**Q：通知会不会丢？**
会“合并”。任务通知有一个计数值，连续 `Give` 多次，`ulTaskNotifyTake(pdTRUE)` 一次清空，控制任务只跑一次。对“只要最新姿态”的场景这是优点；对“每条命令都要执行”的场景不能用通知，要用队列/信号量。

**Q：`xQueueOverwrite` 能不能在中断里用？**
不能。ISR 里只有 `xQueueOverwriteFromISR` 一类变体可用，而且 `xQueueOverwrite` 本身只允许长度 1 的队列。

**Q：多读者同时 `Peek` 会不会读到一半新一半旧？**
不会。队列拷贝在临界区里完成，`Peek` 按值拷贝整个结构体；两个读者可能拿到不同版本，但每个版本都是完整的。

**Q：为什么姿态结构体要带 `tick`？**
判断数据龄期。控制任务可以用 `xTaskGetTickCount() - a.tick` 判断这帧是不是太旧，比只看 `Peek` 返回值更可靠（队列里有旧帧时 `Peek` 也成功）。

### 翻车点

- 把 `xQueueOverwrite` 说成“普通队列也能做到”——普通队列长度 1 时写满会阻塞或失败，覆盖语义是 Overwrite 独有的。
- 说“通知比队列好，所以都用通知”——通知不能多对一、不能带数据（只能带一个 32 位值）。
- 忘了 `pdTRUE` 的清零语义，导致“多次通知只处理一次”被说成 bug。

### 30 秒口述骨架

`旧方案轮询有相位差 → 覆盖邮箱只留最新 → Peek 多读者 → 通知唤醒控制任务 → pdTRUE 清计数 → 队列管消费、通知管唤醒`

### 工作区补充：事件组 + 双队列 + 通知，三种机制同时存在

`FreertosGUILab` 把“事件驱动”拆得更细：

| 机制 | 用在哪 | 语义 |
|---|---|---|
| 任务通知 | ADC DMA 完成 → 浮点换算任务（`waveFormCapture.c:152,161`） | 一对一唤醒，“有新帧了” |
| 事件组 | 浮点任务/按键/DMM → LCD 任务（`LCD_TASK.c:137`） | 多事件位，“哪些面板要重绘”，可合并 |
| 普通队列 | 按键扫描 → 按键工作/慢按键任务（`keyTask.c:21-51`） | 每个按键事件都要执行，消费型 |
| 二值信号量 | SPI DMA 发送完成 → LCD 任务（`LCD_TASK.c:96,197`） | “这一笔发送完成了” |

关键细节：

1. **事件组在调度器启动前静态创建**：`vLCDEventGroupInit()` 用 `xEventGroupCreateStatic()`（`LCD_TASK.c:29-31`），在 `main.c:259` 调度器启动前调用；否则 ADC 注入中断可能先 `xEventGroupSetBitsFromISR`，对 NULL 句柄操作直接崩。
2. **`xEventGroupSetBitsFromISR` 依赖定时器守护任务**：它把“置位”动作 deferred 到 Timer Service Task，所以必须 `configUSE_TIMERS=1`（工作区是 1，CARTEST 是 0）。CARTEST 若在 ISR 里调这个 API，会因为没开 timers 而失败。
3. **双队列分流**：`xKeysQue` 放轻量回调，`xSlowKeyQue` 放重算波表/改时基这类慢回调；`KEYSLOW` 是唯一消费者，天然串行，避免两个慢回调并发改 DAC/TIM5。
4. **双缓冲发布**：`ucShowIdx` 单字节写作为“发布”，LCD 读到的永远是完整一帧（`waveFormCapture.c:169-176`）。

面试可以这样对比：“队列保证每条都处理，通知保证最新一帧唤醒，事件组保证多个 UI 事件不丢位；三者不是替代关系，是语义不同。”

## F08 任务优先级 vs 中断优先级

### 一句话答案

这是两套完全不同的编号体系：**任务优先级 0~6，数值越大越高**（`configMAX_PRIORITIES=7`）；**中断优先级 0~15，数值越小越高**；只有优先级数值 **≥ `configMAX_SYSCALL_INTERRUPT_PRIORITY`（本项目=5）** 的中断才能调用 `xxxFromISR` API。

### 两套模型对照

| 维度 | 任务优先级 | 中断优先级 |
|---|---|---|
| 范围 | 0 ~ `configMAX_PRIORITIES-1`（本项目 0~6） | 0 ~ 15（4 位，分组后有效位数更少） |
| 方向 | **数值越大越优先** | **数值越小越优先** |
| 配置位置 | `xTaskCreate` 第 5 个参数 | `HAL_NVIC_SetPriority(IRQn, preempt, sub)` |
| 谁比较 | 调度器 `vTaskSwitchContext` | NVIC 硬件 |
| 上限宏 | `configMAX_PRIORITIES` | `configMAX_SYSCALL_INTERRUPT_PRIORITY`（门槛，不是上限） |
| 本项目值 | ctrl=4、att=3、motor=5、rc=2、UART2_TX=2、MemMon=1 | TIM2=5、USART3=5、EXTI/ADC/TIM1/TIM3/TIM4/DMA=6 |

### 项目里的真实编排

`main.c:159-175` 在**所有 `MX_*_Init()` 之后**统一重设中断优先级，注释写得很清楚：

```c
HAL_NVIC_SetPriority(TIM2_IRQn,        5U, 0U);  // HAL 1ms 时基，回调里 vTaskNotifyGiveFromISR
HAL_NVIC_SetPriority(USART3_IRQn,      5U, 0U);  // 蓝牙整帧，回调里 xSemaphoreGiveFromISR
HAL_NVIC_SetPriority(EXTI3_IRQn,       6U, 0U);  // 编码器，高频，不调 RTOS API
HAL_NVIC_SetPriority(ADC1_2_IRQn,      6U, 0U);
...
```

两条规则：

1. **会调 `FromISR` 的中断，数值必须 ≥ 5**（TIM2、USART3）。因为 FreeRTOS 临界区把 `BASEPRI` 设成 `5<<4`，只会屏蔽“数值 ≥5”的中断；如果 TIM2 配成 4，它不受临界区保护，却去调 `vTaskNotifyGiveFromISR`，会破坏内核链表。
2. **高频但不调 RTOS 的中断，压到 6**（EXTI/ADC/TIM1/TIM3/TIM4/DMA）。它们不能压过 TIM2 的 tick，否则系统时基被饿死，`HAL_GetTick` 不涨、调度节拍丢失。

### FreeRTOSConfig 里的三个关键宏

- `configMAX_PRIORITIES = 7`（`FreeRTOSConfig.h:109`）：任务优先级上限，和中断无关。
- `configKERNEL_INTERRUPT_PRIORITY = 15<<4`（`:325`）：PendSV/SysTick 的优先级，最低。
- `configMAX_SYSCALL_INTERRUPT_PRIORITY = 5<<4`（`:333`）：FromISR 调用门槛，写进 `BASEPRI`。

`port.c` 里 `vPortEnterCritical()` 做 `msr basepri, #(5<<4)`，`vPortExitCritical()` 在嵌套计数归零时 `msr basepri, #0`——这就是“临界区只屏蔽 5 及以下（数值≥5）中断”的硬件实现。

### 你模拟面试的硬伤（必须纠正）

`CARTESTFreertos/面试评分总结.md` Q2 记录：你把中断约束答成了“优先级高于等于 `configMAX_PRIORITIES`”。

正确表述只有一句：

> **只有优先级数值 ≥ `configMAX_SYSCALL_INTERRUPT_PRIORITY` 的中断，才能调用 `xxxFromISR`。`configMAX_PRIORITIES` 是任务优先级数量，跟中断半毛钱关系没有。**

记忆锚点：**“SysCall 门槛管中断，MAX_PRIORITIES 管任务”**。

### 追问与答法

**Q：ISR 里为什么不能调 `xQueueSend`？**
`xQueueSend` 可能会阻塞、会进临界区、会操作调度器链表；ISR 不能阻塞，且调度器正在被打断。ISR 只能用 `xQueueSendFromISR`，并通过 `pxHigherPriorityTaskWoken` 告诉内核“是否需要退出中断时立刻切换”。

**Q：`portYIELD_FROM_ISR` 做了什么？**
如果 `xHigherPriorityTaskWoken == pdTRUE`，写 PendSV 置位位，请求在中断退出后立刻切换；否则直接返回。项目里 `app_rc.c:87`、`app_usart2_dma.c:34`、`main.c:834` 都是这个套路。

**Q：任务优先级数值大，为什么中断数值小？**
任务优先级是 FreeRTOS 软件定义的“排队序号”；中断优先级是 ARM NVIC 硬件定义的“抢占等级”，ARM 规定数值越小优先级越高。两套标准不同，不能类比。

**Q：优先级反转是什么？**
低优先级任务持有互斥量，高优先级任务等它，中优先级任务又把低优先级任务抢占，导致高优先级任务被中优先级任务间接拖住。解决：优先级继承（`xSemaphoreCreateMutex`）或优先级天花板。本项目没用互斥量，但面试要能答。

### 翻车点

- 把 `configMAX_PRIORITIES` 当成中断优先级上限（你的原硬伤）。
- 说“中断优先级数值越大越高”。
- 说“所有中断都能调 FromISR，只要用对函数名”——优先级不满足 ≥5 照样崩。

### 30 秒口述骨架

`任务 0~6 越大越高 → 中断 0~15 越小越高 → FromISR 门槛 5 → BASEPRI 屏蔽 ≥5 → TIM2/USART3=5、高频=6 → MAX_PRIORITIES 只管任务`

### 工作区补充：一张真实的中断优先级表

`FreertosGUILab` 的 `configMAX_PRIORITIES = 5`（任务优先级只有 0~4），中断优先级如下：

| 中断 | 优先级 | ISR 里调用的 API | 是否满足 ≥5 |
|---|---|---|---|
| EXTI3（波形触发） | 5 | `xTimerStartFromISR` / `xTimerResetFromISR` | 是 |
| DMA1_CH3（USART1 TX） | 5 | `xSemaphoreGiveFromISR` | 是 |
| DMA1_CH4（SPI1 TX） | 5 | `xSemaphoreGiveFromISR` | 是 |
| DMA1_CH1（ADC DMA 完成） | 6 | `vTaskNotifyGiveFromISR` | 是 |
| ADC1_2（注入组） | 15 | `xEventGroupSetBitsFromISR` | 是 |

这张表比背定义好用：**只要 ISR 里出现 `xxxFromISR`，优先级数值就必须 ≥5；数值越大优先级越低，15 是最低、最安全**。反过来，不调 RTOS API 的高频中断可以比 5 更“高”（数值更小），但项目里没有这么配。

另外注意：`configMAX_PRIORITIES=5` 和 `configMAX_SYSCALL_INTERRUPT_PRIORITY=5<<4` 里的两个“5”只是数字碰巧相同，含义完全不同——前者是任务优先级数量，后者是中断 API 门槛。面试最爱在这里挖坑。
