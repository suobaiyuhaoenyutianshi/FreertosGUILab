## D01 HardFault 抓现场（MSP/PSP）

### 一句话答案

Cortex-M 进异常时，硬件自动把 **R0-R3、R12、LR、PC、xPSR 共 8 个字**压进“当时正在用的栈”；用 `EXC_RETURN` 的 bit2 判断用的是 **MSP（中断/内核）还是 PSP（任务）**；项目里用 `HF_DUMP_FRAME()` 选栈后尾调用 `hardfault_dump()`，把现场抄进全局 `hf_ctx` 再 `while(1)`，调试器 Watch 一个结构体就能看全部。

### 原理链（5 步）

1. **硬件压帧**：顺序固定，低地址在前。
   `stack[0]=R0, [1]=R1, [2]=R2, [3]=R3, [4]=R12, [5]=LR, [6]=PC, [7]=xPSR`。
2. **判断栈**：进异常时 LR 被写成 `EXC_RETURN`。
   - `0xFFFFFFF9` → 崩在 Handler 模式（中断里），用 **MSP**；
   - `0xFFFFFFFD` → 崩在 Thread 模式（任务里），用 **PSP**。
3. **选栈**：`tst lr, #4` 测 bit2。bit2=0 → MSP，bit2=1 → PSP。这就是 `HF_DUMP_FRAME` 里 `ite eq / mrseq r0,msp / mrsne r0,psp` 的来源。
4. **抄现场**：`hardfault_dump(stack, exc_return)` 把 8 个字 + `HFSR/CFSR/BFAR/MMFAR` + 当前任务句柄/任务名全部存进 `hf_ctx`，然后 `while(1)` 停住。
5. **定罪**：先看 `exc_return` 决定查任务还是中断；再看 `pc` 去反汇编/`addr2line` 找具体指令；用 `cfsr` 判断错误类型，用 `bfar` 确认坏地址。

### 项目证据

`Core/Src/stm32f1xx_it.c:42-50`：

```c
#define HF_DUMP_FRAME()                       \
    __asm volatile (                          \
        "tst lr, #4       \n"                 \
        "ite eq           \n"                 \
        "mrseq r0, msp    \n"                 \
        "mrsne r0, psp    \n"                 \
        "mov r1, lr       \n"                 \
        "b hardfault_dump \n"                 \
    )
```

- `b` 是尾调用，不是 `bl`：不压返回地址、不改 LR，因为异常帧里的 LR 本身就是要保存的现场。
- `Core/Src/stm32f1xx_it.c:88-136`：`hf_ctx_t` 结构体 + `hardfault_dump()`；`hf_ctx` 是 `volatile`，调试器暂停后直接 Watch。
- `:175-230`：HardFault / MemManage / BusFault / UsageFault 四个 Handler 都调 `HF_DUMP_FRAME()`。
- `:125-133`：`xTaskGetCurrentTaskHandle()` + `pcTaskGetName()` 记录“崩在哪个任务”；调度器没起来时句柄为 NULL，跳过，避免二次崩溃。

### 现场怎么读（按顺序）

| 顺序 | 看什么 | 判断 |
|---|---|---|
| 1 | `hf_ctx.exc_return` | `0xFFFFFFFD` → 任务（PSP）；`0xFFFFFFF9` → 中断（MSP） |
| 2 | `hf_ctx.pc` | 出错指令地址，`addr2line -e xxx.elf 0x0800xxxx` |
| 3 | `hf_ctx.lr` | 谁调用进来的（返回地址） |
| 4 | `hf_ctx.r0~r3` | 函数参数，坏地址常躺在里面 |
| 5 | `hf_ctx.psr` 低 9 位 | 0=线程，3=HardFault，16+n=第 n 个 IRQ |
| 6 | `hf_ctx.hfsr` | bit30 FORCED=1 → 真凶在 CFSR |
| 7 | `hf_ctx.cfsr` | 细分原因（见 D03） |
| 8 | `hf_ctx.bfar` | `BFARVALID=1` 时才可信 |
| 9 | `hf_ctx.task_name` | 空 = 调度器还没起来 |

### 一个必须会说的边界

**`hf_ctx` 全 0 不代表“没有 HardFault”**，而通常说明：

- 根本没进 HardFault（可能是任务跑穿、死锁、被看门狗复位）；
- 或者进的是 `Default_Handler` / 启动文件里的死循环，没走你的 `hardfault_dump`；
- 或者现场在复位后已经被 `.bss` 清零。

所以判断逻辑树是：先看 `hf_ctx` 是否全 0 → 再看 `exc_return` → 再看 `CFSR`。这一步是你调试方法论里“先分类再定位”的典型应用。

### 追问与答法

**Q：为什么不能在 HardFault 里 `printf`？**
`printf` 可能用堆、用信号量、用串口中断，而 HardFault 优先级高于可屏蔽中断，且堆/内核可能已经损坏；一旦再次触发 fault 或死等，现场就丢了。正确做法是只写全局变量 + `while(1)`。

**Q：为什么 CFSR/BFAR 要先存再分析？**
CFSR 是“读清”寄存器，读一次就可能把状态位清掉；调试器 Watch 多次读，第一次的值最珍贵。项目里 `hardfault_dump()` 进函数先存一份，就是为了这个。

**Q：`STKERR` 说明什么？**
异常入栈时总线错误，常见于栈指针越界/栈溢出把 SP 指到非法区域。配合 `uxTaskGetStackHighWaterMark` 和栈尾 `0xA5` 检查一起看。

### 翻车点

- 崩在任务里却去读 MSP（应该 PSP）。
- 把 `0xFFFFFFF9`/`0xFFFFFFFD` 记反。
- 认为 `hf_ctx` 全 0 就是“HardFault 没发生”——要先排除复位/死锁/Default_Handler。

### 30 秒口述骨架

`硬件压 8 字 → LR=EXC_RETURN → tst lr,#4 选 MSP/PSP → 存 hf_ctx → while(1) → PC 定罪 → CFSR 佐证`

### 工作区补充：两套可以亲手复现的 HardFault 实验

`FreertosGUILab` 把“抓现场”做成了练习，`Core/Src/main.c:112-174` 有两个宏：

| 宏 | 触发方式 | 预期故障 |
|---|---|---|
| `EXERCISE_CRASH_ENABLE` | 向 `0x30000000` 写数据（`main.c:142-143`） | BusFault → HardFault，`IMPRECISERR` |
| `EXERCISE_JUMP_ENABLE` | 调用偶数地址 `0x20004e00` 函数指针（`main.c:171-172`） | UsageFault → HardFault，`INVSTATE` |

两个实验都先 `vTaskDelay(1000)` 再崩，给你时间连调试器。`stm32f1xx_it.c:89-159` 的 `hf_ctx` 一次性存下 r0-r3/r12/lr/pc/psr/exc_return/hfsr/cfsr/bfar/mmfar/sp/cur_task/task_name，暂停后 Watch 一个结构体就能读全。

这比“看别人写的 HardFault 案例”强：你可以自己改宏、烧录、暂停、读 `hf_ctx`，把 D01/D03 的每个字段和真实故障对上号。

## D03 CFSR 五位怎么看

### 一句话答案

`SCB->CFSR` 分三段：**MMFSR[7:0] 内存管理、BFSR[15:8] 总线、UFSR[31:16] 用法**；最常看的“五位”是 BFSR 的 **IBUSERR(8)、PRECISERR(9)、IMPRECISERR(10)、STKERR(12)、BFARVALID(15)**。先看 `HFSR.FORCED` 确认是升级来的，再按“精确/不精确/取指/入栈”顺序判。

### 寄存器结构

```
bit 31..16  UFSR  UsageFault
bit 15..8   BFSR  BusFault
bit  7..0   MMFSR MemManage
```

### BFSR 五位（背这张表）

| 位 | 名称 | 含义 | 现场可信度 |
|---|---|---|---|
| 8 | `IBUSERR` | 取指令总线错误 | PC 可能跑飞，看 `pc`/`lr` |
| 9 | `PRECISERR` | **精确**数据访问总线错误 | `BFAR` 有效，直接看坏地址 |
| 10 | `IMPRECISERR` | **不精确**总线错误（写缓冲延迟上报） | `BFAR` 无效，只能反汇编 |
| 12 | `STKERR` | 异常入栈错误 | 栈指针越界/栈溢出 |
| 15 | `BFARVALID` | BFAR 里的地址是否有效 | 只有=1 才信 BFAR |

### UFSR 常看五位

| 位 | 名称 | 典型原因 |
|---|---|---|
| 16 | `UNDEFINSTR` | 执行到非法指令（函数指针错位、跳飞） |
| 17 | `INVSTATE` | EPSR.T=0（Thumb 位丢失，常见于函数指针低比特被清掉） |
| 18 | `INVPC` | 异常返回时 PC 非法 |
| 24 | `UNALIGNED` | 非对齐访问（开了 UNALIGNED_TRAP 才会报） |
| 25 | `DIVBYZERO` | 除零（开了 DIV_0_TRP 才会报） |

### 判读逻辑树

```
HFSR.FORCED == 1 ?
  ├─ 是 → 看 CFSR
  │     ├─ BFSR.PRECISERR=1 && BFARVALID=1 → 坏地址明确，查 BFAR
  │     ├─ BFSR.IMPRECISERR=1 → BFAR 不可信，反汇编重建
  │     ├─ BFSR.IBUSERR=1 → 取指跑飞，查 PC/LR/函数指针
  │     ├─ BFSR.STKERR=1 → 栈越界，查 SP/栈水位
  │     └─ UFSR.UNDEFINSTR/INVSTATE → 函数指针/跳转表被踩
  └─ 否 → 看 HFSR.VECTTBL / DEBUGEVT，或不是 HardFault（复位/死锁）
```

### 项目证据与真实案例

- 抓取位置：`Core/Src/stm32f1xx_it.c:119-122`
  ```c
  hf_ctx.hfsr  = SCB->HFSR;
  hf_ctx.cfsr  = SCB->CFSR;
  hf_ctx.bfar  = SCB->BFAR;
  hf_ctx.mmfar = SCB->MMFAR;
  ```
  顺序很重要：先存再分析。
- **项目踩过的坑**：队列收发结构体格式不一致（发送端整体移位 1 字节，接收端仍按原长度解包），函数指针字段被垃圾数据覆盖，调用时取指总线错误 → `IBUSERR`/`UNDEFINSTR`，`pc` 指向一个不像代码的地址。修复是让收发两端结构体严格对齐。
- **另一个案例**：rc 任务 1KB 栈里跑 `sscanf` + `vsnprintf` 爆栈，典型表现是 `STKERR` 或栈尾 `0xA5` 被改写后进 `vApplicationStackOverflowHook`。

### 追问与答法

**Q：PRECISERR 和 IMPRECISERR 的区别？**
PRECISERR 是精确总线错误，出错地址就是 BFAR，能直接定位；IMPRECISERR 是写缓冲延迟上报，CPU 已经往前跑了几条指令，BFAR 不可信，只能靠反汇编和 `pc/lr` 推。

**Q：CFSR 读一次会清吗？**
会。它是读清寄存器（写 1 也可清）。所以第一次读到的值最珍贵，必须先存到 RAM 全局变量。

**Q：`INVSTATE` 为什么常见于函数指针？**
Cortex-M 要求 Thumb 指令，函数指针最低位必须是 1（表示 Thumb）。如果指针被踩掉最低位，`bx` 过去 EPSR.T=0，直接 `INVSTATE`。

**Q：MemManage 和 BusFault 怎么区分？**
看 CFSR 低 8 位（MMFSR）还是 8~15 位（BFSR）。MPU 权限违规是 MemManage；访问不存在的总线/外设是 BusFault。F103 默认没开 MPU，所以多数是 BusFault。

### 翻车点

- 把 CFSR 当成“一个位”，不知道它是三段拼起来的。
- 看到 `IMPRECISERR` 还拿 BFAR 当坏地址。
- 看到 `FORCED=1` 就停在这里，不往下看 CFSR。

### 30 秒口述骨架

`CFSR 三段 → BFSR 五位 → FORCED 先看 → 精确看 BFAR → 不精确反汇编 → IBUSERR 查指针 → STKERR 查栈`

### 工作区补充：两个真实 CFSR 样本

`FreertosGUILab` 的两个练习正好覆盖 BFSR 和 UFSR 两类：

1. **写 `0x30000000`**（`main.c:135-144`）
   - 该地址在 F103 存储映射里无对应外设/内存；
   - 写缓冲延迟上报 → `IMPRECISERR`（CFSR=0x400），`BFARVALID=0`，BFAR 不可信；
   - 定位方法：反汇编 `hf_pc` 附近的 `STR`，`R3` 里就是 `0x30000000`。
2. **调用偶数地址函数指针**（`main.c:163-173`）
   - Cortex-M 只认 Thumb（地址最低位=1），偶数地址 bit0=0 → `INVSTATE`（CFSR=0x20000）；
   - `R3/PC` 看起来都像“正常地址”，只能靠 CFSR 的 bit17 + PC 偶数识别；
   - 代码里先 `SCB->SHCSR |= SCB_SHCSR_USGFAULTENA_Msk`，让 UsageFault 亲自接管，否则会升级成 HardFault，`hf_psr` 的 IPSR 从 6 变 3。

这两个样本把 D03 的“先精确后不精确、IBUSERR 查指针、INVSTATE 查 Thumb 位”全部落到了可复现实验上。

## D09 IWDG 500ms 与喂狗位置

### 一句话答案

IWDG 用 **LSI≈40kHz** 独立时钟，超时 `T = 预分频 × (Reload+1) / 40000`；项目实际配 `Prescaler=4、Reload=4095`，得到 **0.41s**；500ms 可以配 `Prescaler=32、Reload=624`。喂狗位置项目放在 **MemMon 任务每 100ms 喂一次**，更严谨的做法是放在最关键的 5ms 控制环——“狗要看着你这条业务线还活着”。

### 计算公式（先纠正一个常见错）

正确公式：

```
T = Prescaler × (Reload + 1) / f_LSI
f_LSI ≈ 40 kHz（F103 典型值，实际 30~60 kHz，所以时间有 ±25% 以上容差）
```

> `C:\flushbonading\debugging\FreeRTOS钩子函数与独立看门狗.md:194-199` 里的公式写成“LSI频率 / (PR预分频) × RLR”，量纲是错的；以本文公式为准。

### 项目实际值

`Core/Src/main.c:395-416`：

```c
hiwdg.Instance = IWDG;
hiwdg.Init.Prescaler = IWDG_PRESCALER_4;   // 4 分频
hiwdg.Init.Reload    = 4095;               // 重装载值
HAL_IWDG_Init(&hiwdg);
```

```
T = 4 × (4095+1) / 40000 = 4 × 4096 / 40000 = 0.4096 s ≈ 410 ms
```

调试记录里的复位周期 0.417~0.484s，正好对上“410ms + 开机时间/等指令时间”。

### 500ms 怎么配

| 方案 | Prescaler | Reload | 实际 T |
|---|---|---|---|
| A | 32（`IWDG_PRESCALER_32`） | 624 | 32×625/40000 = **0.500 s** |
| B | 64（`IWDG_PRESCALER_64`） | 312 | 64×313/40000 = **0.5008 s** |
| C | 4（项目值） | 4999 | 4×5000/40000 = **0.500 s**（Reload 上限 4095，不可行） |

方案 A 最直接；注意 Reload 是 12 位，最大 4095，所以低分频配不出 500ms。

### 喂狗位置：三种哲学

| 方案 | 位置 | 证明了什么 | 风险 |
|---|---|---|---|
| A | `vApplicationIdleHook` | 空闲任务还能跑 | 看不住“高优先级任务死循环”，也看不住“中断占死” |
| B | 主控制任务（5ms） | **控制环还活着** | 最贴合业务；调试断点会被狗复位，要 FREEZE |
| C | 独立监控任务（项目现状） | 系统调度还在跑 | 控制环死了但监控任务活着时，狗不响 |

项目选 C：`memory_monitor.c:45-49` 每轮循环先 `HAL_IWDG_Refresh(&hiwdg)`，`MONITOR_FEED_INTERVAL_MS = 100`（`memory_monitor.h:28-30`），即 **100ms 喂一次，410ms 超时**，留 4 倍余量。

为什么可以接受：MemMon 优先级 1，只要它还能被调度，说明没有更高优先级任务把 CPU 占死；但如果控制任务自己卡死而 MemMon 正常，狗不会复位——这是当前方案的盲区。更严谨的做法是把喂狗放进 `App_Control_Task` 的 5ms 循环，或做“多任务签到 + 全部签到才喂”的组合。

### 三个必须处理的工程细节

1. **初始化窗口**：`MX_IWDG_Init()` 一调用狗就开始跑，但调度器还没起、没人喂。项目在长初始化（MPU6050 的 100ms 等）之后补喂一次：`main.c:199-201`。
2. **调试冻结**：`main.c:157` `__HAL_DBGMCU_FREEZE_IWDG()`，断点暂停时狗停走，否则一暂停就复位。
3. **复位来源**：`RCC_CSR` 的 `IWDGRSTF` 判断本次是不是狗复位；项目调试记录就是靠“B1 周期性重复 + 0.41s 间隔”反推出狗复位。

### 追问与答法

**Q：IWDG 和 WWDG 区别？**
IWDG 用 LSI，独立于主时钟，主时钟停了也能复位，但精度差；WWDG 用 APB1 时钟，有“窗口”——喂早了也复位，能检测程序跑太快/跑飞，但依赖主时钟。

**Q：喂狗能放中断里吗？**
可以但不推荐。放高优先级定时器中断里，只要中断还在跑就喂，证明不了任务还活着；放低优先级中断又可能被高优先级中断饿死。最好放在“业务主循环”里。

**Q：LSI 不准，500ms 会不会变成 300ms？**
会。F103 LSI 典型 40kHz、范围约 30~60kHz，所以 500ms 实际可能在 0.33~0.67s。喂狗周期必须按最坏情况留足余量（项目 100ms 对 410ms，安全）。

**Q：看门狗能替代掉线检测吗？**
不能。看门狗看“CPU 还活着”，掉线检测看“对端还发不发数据”；对端掉线时本机 CPU 完全正常，狗不会响。

### 翻车点

- 用错公式（把 LSI 频率乘在分子上）。
- 忘记 `Reload+1`（4095 对应 4096 个计数）。
- 认为“喂狗越频繁越好”——喂太勤会让真故障被掩盖，周期应小于超时但不要小到 1ms。

### 30 秒口述骨架

`LSI 40k → T=PR×(RLR+1)/40k → 项目 4/4095=410ms → 500ms 用 32/624 → MemMon 100ms 喂 → 控制环喂更严谨 → FREEZE + 初始化补喂`

### 工作区补充：一个反面案例——开了狗却没喂

`FreertosGUILab` 的 `MX_IWDG_Init()` 参数和平衡车一样（`Prescaler=4、Reload=4095`，0.41s），但 `main.c:254-256` 把它注释掉了，原因写在注释里：

> IWDG 暂不启用：CubeMX 6.18 重新生成时自动勾上了看门狗，但全工程没有喂狗点，0.41s 就会复位一次，表现为 LCD 花屏 + 闪烁。若以后要用，需配套 `HAL_IWDG_Refresh()`。

这个案例回答了两个高频追问：

- **“看门狗开了会怎样？”** 没有喂狗点就是 0.41s 复位循环，现象是屏幕反复花屏/闪烁，不是“程序跑飞”。
- **“喂狗放哪？”** 先确定“谁是这条业务线的命根子”，再在那个任务/循环里喂；没有喂狗点之前，宁可不启动 IWDG。

对比：平衡车项目有 MemMon 每 100ms 喂狗，所以能开；示波器项目没有喂狗点，所以必须关。**看门狗不是“开了更安全”，是“有喂狗点才安全”。**

## D10 掉线检测（心跳计数）

### 一句话答案

每收到一帧就刷新“最后接收时间戳/接收计数”，主循环用 `now - last > 阈值` 判离线；时间用**无符号相减**天然处理回绕。项目里有两套：板间链路 500ms 判离线，电机反馈 100ms 判离线，并且掉线后立即把控制量清零。

### 原理链（4 步）

1. **心跳源**：对端周期发帧（C8T6→F427 的 0x102、电机→主控的 0x201 反馈）。
2. **刷新**：接收回调/路由处理里更新 `last_tick`，并 `rx_cnt++`。
3. **判离线**：`(HAL_GetTick() - last_tick) < 阈值` → 在线；否则离线。无符号减法在 32 位回绕时仍正确。
4. **降级动作**：离线后不能继续用旧值输出——项目里 `main.c:146-157` 收不到 0x201 反馈就把电流指令 `ramp = 0`，避免“电调掉线了、主控还在按旧值输出”。

### 项目证据（test427）

**板间链路（500ms）**：

- `Core/Src/user_motor.c:164-195` `Link_Handler()`：每帧更新
  ```c
  g_link.last_tick = HAL_GetTick();
  g_link.rx_cnt++;
  ```
- `Core/Src/user_motor.c:316-321` `Link_Poll()`：
  ```c
  g_link.online = (uint8_t)((HAL_GetTick() - g_link.last_tick) < LINK_OFFLINE_MS);
  ```
  `LINK_OFFLINE_MS = 500`（`user_motor.h:116`）。

**电机反馈（100ms）**：

- `user_motor.c:157-158`：每帧 `g_motor[index].rx_cnt++`。
- `user_motor.c:326-349` `Motor_Is_Online()`：
  ```c
  if (g_motor[index].rx_cnt != last_cnt[index]) {
      last_cnt[index]  = g_motor[index].rx_cnt;
      last_tick[index] = now;
  }
  return (now - last_tick[index]) < MOTOR_OFFLINE_MS;
  ```
  用“计数有没有变化”判断这轮有没有新帧，避免每帧都读 tick；`MOTOR_OFFLINE_MS` 在 `user_motor.h:90` 附近。

**丢包统计（seq）**：

```c
uint8_t gap = (uint8_t)(frame->data[1] - g_link.seq - 1U);
if (gap != 0U && gap < 128U) g_link.lost_cnt += gap;
```

- 正常连续：`seq - last - 1 = 0`；
- 丢 1 帧：差 2 → gap=1；
- uint8 回绕：`0 - 255 - 1 = 0`（溢出），不会误报；
- `gap >= 128` 视为乱序/重传，不计丢包。

### 阈值怎么定

- 发送周期 × 3 左右：对端 100Hz（10ms）→ 100ms 阈值能容忍连续丢 9 帧；板间 100Hz → 500ms 容忍 49 帧，偏保守。
- 太小：总线偶发错误就误判断线；太大：真掉线后半天才降级。
- 最好和“故障等级”绑定：短暂丢失 → 报警；持续丢失 → 停车/失能。

### 追问与答法

**Q：`HAL_GetTick()` 回绕怎么办？**
用无符号减法：`now - last` 在 32 位回绕时仍得到正确的“经过的 tick 数”（只要间隔小于 2^32 ms ≈ 49 天）。不要写 `now > last + timeout`。

**Q：心跳计数和看门狗的区别？**
看门狗看“本机 CPU 是否还活着”；心跳看“对端是否还发数据”。对端掉线时本机 CPU 正常，狗不会响，所以两套都要有。

**Q：为什么用 `rx_cnt` 变化而不是每帧读 tick？**
减少每帧一次 `HAL_GetTick()` 调用；只在轮询时比较计数，逻辑更省。缺点是“重复帧也会让计数增加”，如果要检测“重复帧/卡死帧”，要改成“数据内容变化”或“seq 变化”。

**Q：掉线后应该怎么做？**
分级：先报警（LED/串口），再把控制量归零/保持最后安全值，最后失能电机。项目里直接 `ramp = 0`，属于“立即降级”。

### 翻车点

- 用 `now > last + timeout` 判超时（回绕出错）。
- 只做检测不做降级动作（检测到掉线还继续按旧值输出）。
- 把 100ms 阈值用在 10ms 周期的总线上，偶发丢一帧就误判。

### 30 秒口述骨架

`帧刷新 last_tick/rx_cnt → now-last>阈值 → 无符号减法抗回绕 → seq 差值算丢包 → 掉线清零输出 → 狗看自己、心跳看对端`

## C01 CAN 位时序（1Mbps 怎么配）

### 一句话答案

CAN 一位 = **SyncSeg(1TQ) + BS1 + BS2**；项目 `test427` 的 APB1 = 45MHz，`Prescaler=9` → TQ = 200ns，`BS1=2TQ、BS2=2TQ` → 共 **5TQ = 1µs = 1Mbps**，采样点 = (1+2)/5 = **60%**。

### 原理链（4 步）

1. **时钟源**：F427 系统 180MHz，APB1 四分频 = **45MHz**（`test427/Core/Src/main.c:241-244`：`APB1CLKDivider = RCC_HCLK_DIV4`）。
2. **TQ**：`TQ = Prescaler / f_APB1 = 9 / 45MHz = 200ns`。
3. **位时间**：`1 + BS1 + BS2 = 1 + 2 + 2 = 5 TQ`，`5 × 200ns = 1µs` → **1Mbps**。
4. **采样点**：`(1 + BS1) / 总TQ = 3/5 = 60%`；`SJW = 1TQ`。

### 项目证据

`test427/Core/Src/can.c:40-52`：

```c
hcan1.Init.Prescaler         = 9;
hcan1.Init.Mode              = CAN_MODE_NORMAL;
hcan1.Init.SyncJumpWidth     = CAN_SJW_1TQ;
hcan1.Init.TimeSeg1          = CAN_BS1_2TQ;
hcan1.Init.TimeSeg2          = CAN_BS2_2TQ;
hcan1.Init.AutoBusOff        = ENABLE;
hcan1.Init.AutoRetransmission = DISABLE;
```

`test427/Core/Src/user_motor.c:203-207` 的注释也把算式写出来了：

```
APB1 = 45 MHz，Prescaler = 9，BS1 = 2TQ，BS2 = 2TQ
→ 45M / 9 / (1 + 2 + 2) = 1 Mbps
```

### 对应到 BTR 寄存器

STM32F4 bxCAN 的 `CAN_BTR`：

| 字段 | 位 | 项目值 |
|---|---|---|
| `BRP[9:0]` | 9:0 | 8（写入值 = Prescaler-1） |
| `TS1[3:0]` | 19:16 | 1（编码值，实际 2TQ） |
| `TS2[2:0]` | 22:20 | 1（编码值，实际 2TQ） |
| `SJW[1:0]` | 25:24 | 0（1TQ） |

> HAL 的 `CAN_BS1_2TQ` 宏值是 1，不是 2；硬件解释为“编码值+1 个 TQ”。面试如果问“BS1 写 2 还是写 1”，要答“HAL 宏 `CAN_BS1_2TQ` 的编码值是 1，实际是 2 个 TQ”。

### 这个配置的优缺点（要诚实）

- 优点：5TQ 正好整除，1µs 好算，短总线/实验室环境可用。
- 缺点：**采样点只有 60%**，低于 CAN 规范常用的 75%~87.5%（CiA 推荐 87.5%）；TQ 只有 200ns，`SJW=1TQ` 对晶振误差/总线延迟的容忍度小，长总线或节点多时容易出错。
- 更规范的 1Mbps 配法（同样 45MHz）：
  `Prescaler=3` → TQ=66.67ns，`BS1=12TQ、BS2=2TQ` → 15TQ=1µs，采样点 `13/15≈86.7%`，`SJW=1TQ`。
- 面试如果被追问“你怎么验证”：示波器/逻辑分析仪量一位宽度是否为 1µs；读 `CAN->BTR` 确认；逐步增加节点/线长观察错误计数。

### 追问与答法

**Q：采样点怎么算？**
`采样点 = (1 + BS1) / (1 + BS1 + BS2)`。SyncSeg 固定 1TQ，所以分子是 1+BS1，分母是整位的 TQ 数。

**Q：SJW 是干什么的？**
同步跳转宽度，允许重新同步时一次调整的最大 TQ 数。晶振误差大、总线长、节点多时要适当增大；但 SJW 不能超过 BS1/BS2 的可用范围。

**Q：为什么 APB1 是 45MHz 不是 90MHz？**
F427 主频 180MHz，APB1 最大 45MHz（四分频），APB2 最大 90MHz（二分频）。CAN1 挂在 APB1 上，所以只能用 45MHz。

**Q：波特率误差容忍度？**
CAN 要求总误差通常在 0.5% 以内（取决于采样点和 SJW）。用 HSI 内部 RC（项目就是 HSI）比外部晶振误差大，量产建议用外部晶振。

**Q：`AutoBusOff=ENABLE` 和 `AutoRetransmission=DISABLE` 为什么这么配？**
自动 Bus-Off 恢复让节点在总线恢复后能重新上线；关闭自动重传是为了避免总线故障时无限重发阻塞发送邮箱（项目里发送失败会计 `g_can_tx_fail`）。

### 翻车点

- 把 `Prescaler=9` 直接当成“9MHz”。
- 忘记 SyncSeg 的 1TQ，算成 `BS1+BS2=4TQ`。
- 说“采样点 60% 是标准推荐值”——不是，标准常用 87.5%。

### 30 秒口述骨架

`APB1 45M → /9=5M → TQ 200ns → 1+2+2=5TQ → 1µs → 1Mbps → 采样点 60% → 规范做法 15TQ/87.5%`
