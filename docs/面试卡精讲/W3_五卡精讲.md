## C05 串口 DMA + 空闲收变长帧

### 一句话答案

变长帧不能靠“收满 N 字节”判断结束，所以用 **DMA 负责搬字节、IDLE 空闲中断负责断帧**：DMA 把数据悄悄写进缓冲，总线静默超过 1 个字符时间触发 IDLE，回调拿到 `Size` 后切缓冲、重新武装、通知任务。DMA 模式下还必须处理 **HT 半传输不是帧尾**、**FE/NE/ORE 错误会停接收**、**双缓冲防止 DMA 踩任务正在读的内存**这三个坑。

### 原理链（6 步）

1. `HAL_UARTEx_ReceiveToIdle_DMA(&huart3, buf, 64)` 启动：DMA 通道开始搬，同时开 IDLE 中断。
2. 每收一个字节，DMA 自动写 `buf`，CPU 不参与。
3. 一帧发完，线上静默超过 1 个字符时间 → IDLE 标志 → `HAL_UARTEx_RxEventCallback(huart, Size)`，`Size` 是本帧字节数。
4. 回调里：
   - 过滤 `HAL_UART_RXEVENT_HT`（DMA_NORMAL 下收到一半也会触发事件，不是帧尾）；
   - 把当前 DMA 缓冲拷到“成品缓冲”；
   - 翻转 DMA 缓冲下标，重新 `HAL_UARTEx_ReceiveToIdle_DMA` 武装下一帧；
   - `xSemaphoreGiveFromISR` 通知任务。
5. 任务 `xSemaphoreTake` 醒来，在临界区把成品缓冲拷走再解析。
6. 出错（FE/NE/ORE）进 `HAL_UART_ErrorCallback`：HAL 已经 `UART_EndRxTransfer()` 关了接收，必须重新武装，否则永久停收。

### 项目证据（CARTEST 平衡车）

`Core/Src/app_rc.c:21-99`：

```c
static uint8_t  s_dma_buf[2][MAX_leng];       // DMA 交替写
static volatile char s_ready_buf[MAX_leng];   // 只有 CPU 读写
static uint8_t  s_dma_idx = 0;
static SemaphoreHandle_t xLineReady = NULL;
```

回调 `HAL_UARTEx_RxEventCallback`：

```c
if (HAL_UARTEx_GetRxEventType(huart) == HAL_UART_RXEVENT_HT) return;  // 半传输不是帧尾
if (Size > (MAX_leng - 1U)) Size = (MAX_leng - 1U);                   // 收满 64 截到 63
for (i...) s_ready_buf[i] = s_dma_buf[s_dma_idx][i];                  // 拷到成品缓冲
while (行尾 \r\n) Size--;                                             // 去行尾
s_ready_buf[Size] = '\0';
s_dma_idx ^= 1U;                                                      // 换缓冲
HAL_UARTEx_ReceiveToIdle_DMA(&huart3, s_dma_buf[s_dma_idx], MAX_leng); // 重新武装
xSemaphoreGiveFromISR(xLineReady, &xHigherPriorityTaskWoken);
portYIELD_FROM_ISR(xHigherPriorityTaskWoken);
```

错误回调 `app_rc.c:93-99`：

```c
void HAL_UART_ErrorCallback(UART_HandleTypeDef *huart) {
    if (huart != &huart3) return;
    testRcErr++;
    HAL_UARTEx_ReceiveToIdle_DMA(&huart3, s_dma_buf[s_dma_idx], MAX_leng);
}
```

启动检查 `app_rc.c:45-49`：`HAL_UARTEx_ReceiveToIdle_DMA` 返回值不是 `HAL_OK` 就换一块缓冲重试——启动瞬间有挂起错误时 HAL 会返回 `HAL_ERROR` 并把 `ReceptionType` 复位，之后永远不进回调。

### 为什么必须双缓冲

临界区只能挡 CPU 中断，**挡不住 DMA 写内存**。如果任务正在读 `s_dma_buf[0]`，ISR 又翻转下标让 DMA 写 `s_dma_buf[0]`，任务就会读到“半新半旧”的帧。项目的做法是：

- DMA 只写 `s_dma_buf[idx]`；
- ISR 把刚收完的帧拷到 `s_ready_buf`（DMA 永远不碰这块）；
- 任务从 `s_ready_buf` 取，且用 `taskENTER_CRITICAL()` 防止 ISR 在拷贝中途覆盖。

### 对比：test427 的 IT 版

`test427/Core/Src/user_serial.c:70-75` 用 `HAL_UARTEx_ReceiveToIdle_IT`（中断逐字节收，不用 DMA），回调 `:157-170` 里重新挂接收；错误回调 `:185-197` 先清 PE/FE/NE/ORE 标志，再判断 `RxState == READY` 才重挂。适合低波特率/小数据量；数据量大时逐字节中断会吃 CPU。

### 追问与答法

**Q：IDLE 中断什么时候触发？**
总线在一个完整字符时间（起始位+数据位+停止位）内没有新数据，硬件置 IDLE。9600 波特率下一个字符约 1.04ms，所以两条指令之间要留 ≥1 字节时间，否则会被当成一帧或按缓冲长度切。

**Q：DMA 循环模式行不行？**
循环模式下 DMA 会自己回卷，但“一帧到哪里结束”仍然要靠 IDLE；而且回卷会覆盖旧数据，需要额外的读指针管理。项目用 `DMA_NORMAL` + 手动重装，逻辑更直观。

**Q：为什么不用定长接收？**
上位机指令长度不固定（`move 0 0`、`move -100 100` 长度不同），定长要么截断要么等超时。

**Q：半传输（HT）为什么不是帧尾？**
DMA 缓冲 64 字节，收到 32 字节时 HAL 触发 HT 事件，只是为了让你“提前处理一半”，不代表总线空闲；把它当帧尾会把一帧切成两半。

**Q：错误回调里为什么只重装、不重试本帧？**
丢一帧对遥控没影响，下一帧空闲又会来；在 ISR 里重试可能死循环，还可能再次触发错误。

### 翻车点

- 忘了重新武装 → 只能收第一帧。
- 把 HT 当帧尾。
- 以为临界区能挡 DMA。
- DMA 模式下不处理错误回调 → ORE 后永久停收。

### 30 秒口述骨架

`DMA 搬 → IDLE 断帧 → 回调拿 Size → 过滤 HT → 拷成品缓冲 → 翻下标重装 → 错误回调也重装 → 双缓冲防 DMA 踩`

### 工作区补充：DMA 发送链路（和接收链路对照）

`FreertosGUILab` 的 `Core/Src/app_usart1_dma.c:35-65` 是“DMA 发送守门员”：

1. `App_USART1_Printf` 把格式化好的 `char*` 丢进 `xTxQueue`；
2. `UART1_TX` 任务 `xQueueReceive` 取到指针，`HAL_UART_Transmit_DMA` 启动；
3. `HAL_UART_TxCpltCallback` 在 ISR 里 `xSemaphoreGiveFromISR(xTxDmaSem)`（`:23-33`）；
4. 任务 `xSemaphoreTake(xTxDmaSem, 5s)` 等完成，再 `vPortFree`。

和接收链路的分工：

| 方向 | 谁搬数据 | 谁断帧/完成 | 通知谁 |
|---|---|---|---|
| 接收（CARTEST `app_rc.c`） | DMA + IDLE | `HAL_UARTEx_RxEventCallback` | 二值信号量 → rc 任务 |
| 发送（工作区 `app_usart1_dma.c`） | DMA | `HAL_UART_TxCpltCallback` | 二值信号量 → 守门员任务 |

一个值得对比的细节：工作区 `App_USART1_Printf` 入队用 `portMAX_DELAY`（`:94`），CARTEST 改成 `pdMS_TO_TICKS(100)`。原因不是“谁更对”，而是**调用者能不能被阻塞**：CARTEST 的 MemMon 是唯一喂狗任务，它一旦卡在满队列上就是 0.41s 复位；工作区没有启动 IWDG，所以阻塞不会立刻致命。面试时要能说出这个取舍。

## C08 I2C 连读 14 字节

### 一句话答案

MPU6050 的加速度、温度、角速度在寄存器 **0x3B~0x48 连续 14 字节**，用一次 `HAL_I2C_Mem_Read(addr, 0x3B, 8bit, RAW, 14, 50ms)` 连续读回来，再按大端拼成 7 个 `int16_t`；连读保证这 14 字节来自**同一次采样**，也省掉十几次 I2C 事务开销。

### 原理链（5 步）

1. **地址**：7 位地址 0x68 左移 1 位 = `0xD0`（HAL 要 8 位地址）。
2. **寄存器地图**：
   - `0x3B~0x40`：ACC X/Y/Z 高/低字节；
   - `0x41~0x42`：温度；
   - `0x43~0x48`：GYRO X/Y/Z 高/低字节。
3. **一次事务**：
   `START → 0xD0(W) → ACK → 0x3B → ACK → Repeated START → 0xD0(R) → ACK → 连续读 14 字节 → NACK → STOP`。
4. **拼装**：`int16_t ax_raw = (RAW[0]<<8) | RAW[1]`，大端高字节在前。
5. **换算**：
   - 加速度 ±2g：`1 LSB = 2/32768 = 6.1035e-5 g`；
   - 陀螺仪 ±2000°/s：`1 LSB = 2000/32768 = 6.1035e-2 °/s`；
   - 温度：`temp_raw / 333.87 + 21.0`（MPU6500 公式，MPU6050 用注释里的公式）。

### 项目证据

`Core/Src/app_mpu6050.c:111-145`：

```c
uint8_t RAW[14];
if (HAL_I2C_Mem_Read(&hi2c1, MPU6050_ADDR, MPU6050_REG_ACCEL_XOUT_H,
                     I2C_MEMADD_SIZE_8BIT, RAW, 14, MPU6050_I2C_TIMEOUT_MS) != HAL_OK)
{
    return;   // 读失败保留上一次数据，不拿 0/垃圾值解算
}
int16_t ax_raw = (int16_t)((RAW[0]<<8) | RAW[1]);
...
gx = gx_raw * 6.1035e-2f;
```

- `MPU6050_REG_ACCEL_XOUT_H = 0x3B`（`:29`）。
- `MPU6050_I2C_TIMEOUT_MS = 50`（`:19`），注释明确写“绝不能用 `HAL_MAX_DELAY`，总线被拉低会永久死等”。
- I2C1 配置 400kHz：`main.c:371-383`。

### 为什么连读，不单字节读

1. **一致性**：单字节读 14 次，中间传感器可能已经更新，拼出来的姿态是“跨采样时刻”的；连读是一次采样快照。
2. **效率**：每次 I2C 事务都有 START/地址/ACK/STOP 开销，14 次单字节读的时间约是连读的十几倍。
3. **代码简单**：一次调用拿全，不用管寄存器地址递增。

### 时间估算（面试可以现场算）

400kHz 下，1 字节 ≈ 9 个时钟（8 数据+1 ACK）≈ 22.5µs；14 字节 + 地址/寄存器开销 ≈ 0.4ms 左右。姿态任务 5ms 周期，I2C 占用不到 10%，余量充足。

### 追问与答法

**Q：`HAL_I2C_Mem_Read` 和 `HAL_I2C_Master_Receive` 区别？**
`Mem_Read` 自带“先写寄存器地址、再 Repeated START 读”的完整时序；`Master_Receive` 只做读，寄存器地址要自己用 `Master_Transmit` 先写。

**Q：什么是 Repeated START？**
读寄存器时不能先 STOP 再 START，否则总线可能被其他主机抢走；用 Repeated START 在同一个事务里从“写地址”切到“读数据”。

**Q：地址 0x68 还是 0xD0？**
7 位地址是 0x68；HAL 的 `HAL_I2C_Mem_Read` 要 8 位地址，所以左移一位成 0xD0。具体看 HAL 版本/参数约定，项目里用的是 0xD0。

**Q：I2C 时钟拉伸是什么？**
从机来不及处理时把 SCL 拉低，主机必须等；HAL 默认支持。如果从机一直拉低，就会表现为超时，所以超时不能设 `HAL_MAX_DELAY`。

**Q：读失败为什么直接 return？**
失败时 `RAW` 内容未定义，拿 0 去解算会得到“假姿态”（例如 pitch=0 看似水平），比保留上一帧更危险。控制层还会用 `last_good_att` 兜底并累计 `att_fail_cnt`（`app_control.c:96-112`）。

### 翻车点

- 用 7 位地址 0x68 直接传给 HAL（少移一位）。
- 忘记大端拼装，高低字节颠倒。
- 用 `HAL_MAX_DELAY`，总线异常时任务永久卡死。
- 读失败后拿全 0 数据继续解算。

### 30 秒口述骨架

`0x3B 起 14B → 一次 Mem_Read → 大端拼 7 个 int16 → ±2g/±2000dps 换算 → 50ms 超时 → 失败保留旧值`

## E01 Git 分支与提交范围

### 一句话答案

分支策略：**main 始终保持可运行**，功能/修复在独立分支做，合并前自测；提交范围：**只 `git add` 本次改动的具体文件**，提交前 `git status` 确认，代码与文档分开提交；提交信息用 Conventional Commits：`type(scope): 中文描述`。

### 提交范围的操作规范

```bash
git status                 # 先看有哪些改动
git diff                   # 看具体改了什么
git add Core/Src/app_rc.c  # 只加本次相关文件（按文件名）
git diff --cached          # 确认暂存区
git commit -m "fix(rc): ..."
```

为什么不用 `git add -A`：

- 会把调试用的临时文件、`.cache`、`.vscode` 配置、无关的 CubeMX 重新生成文件一起带进去；
- 一次提交混入多个主题，回滚时无法只回滚其中一个；
- 容易误提交密钥/大文件。

### 分支策略（面试标准答法）

| 分支 | 用途 | 合并前 |
|---|---|---|
| `main` | 随时可烧录、可演示 | — |
| `feature/xxx` | 新功能 | 自测 + 编译 0 error |
| `fix/xxx` | 修 bug | 复现步骤 + 修复验证 |
| `docs/xxx` | 纯文档 | 不影响代码 |

合并用 `merge --no-ff` 保留分支历史，或 `rebase` 保持线性；团队规范优先。**不要对已推送的公共分支 rebase**。

### 项目里最值钱的一条经验

`docs/调试记录_蓝牙USART3接收与爆栈复位.md:229-237` 第九节第 6 条：

> **改实现前先提交**：切换接收方案前把当前可用版本提交到 git，避免“直接覆盖、旧版本丢失”。

这条比任何分支模型都实用：你从 RXNE 中断切回 DMA+IDLE 时，如果旧版本没提交，出问题就回不去了。

### 追问与答法

**Q：merge 和 rebase 区别？**
merge 生成一个合并提交，保留分支结构；rebase 把提交“搬”到目标分支末尾，历史线性但会改写 commit hash。公共分支不要 rebase。

**Q：怎么回滚一次提交？**
未推送：`git reset --soft HEAD~1`（保留改动）或 `--hard`（丢弃改动，危险）；已推送：`git revert <hash>` 生成反向提交，安全。

**Q：`.gitignore` 该忽略什么？**
`build/`、`.cache/`、`.vscode/`（如果含个人路径）、`*.o`、`*.elf`、`*.map`、编译数据库 `compile_commands.json`（可选保留）。项目里已有 `.gitignore`，提交前检查有没有漏。

**Q：提交信息写“update”行不行？**
不行。面试官看提交历史就是看你的工程习惯；`update`、`fix bug`、`test` 这类信息等于没写。项目历史里 `f6af870 test`、`bbfd0c8 修`、`3df5c95 ok` 就是反例。

### 翻车点

- `git add -A` 把无关文件带进去。
- 代码和文档混在一个提交。
- 在 main 上直接改、不提交就切方案，旧版本丢失。
- 提交信息只写“修改”。

### 30 秒口述骨架

`main 可运行 → 分支隔离 → 精确 add → status/diff 确认 → type(scope): 中文 → 代码文档分开 → 改实现前先提交`

## E04 CMake 工程结构

### 一句话答案

工程分三层：**CubeMX 生成的 `cmake/stm32cubemx` 子目录**负责芯片/HAL/启动文件/链接脚本；**顶层 `CMakeLists.txt`** 负责工程名、编译选项、链接；**`user_sources.cmake`** 用 `GLOB_RECURSE` 收集 `Core/Src` 和 `freeRTOS/Src`，排除重复的 `system_stm32f1xx.c`，再加头文件路径。

### 三层结构

```
CARTESTFreertos/
├── CMakeLists.txt              # 顶层：project、编译选项、add_subdirectory、size 目标
├── user_sources.cmake          # 用户源文件：GLOB + 排除 + include
├── CMakePresets.json           # 预设：Debug/Release、工具链
├── cmake/
│   ├── gcc-arm-none-eabi.cmake # 交叉编译工具链
│   ├── print_size.cmake        # 打印 Flash/RAM 占用
│   └── stm32cubemx/            # CubeMX 生成：HAL 驱动、启动文件、链接脚本
├── Core/Src、Core/Inc          # 应用代码
├── freeRTOS/Src、freeRTOS/Inc  # FreeRTOS 内核 + FreeRTOSConfig.h
└── Drivers/                    # HAL/CMSIS
```

### 关键代码

`CMakeLists.txt:36-42`：Debug 构型把 `-O0 -g3` 换成 `-Og -g3`。

```cmake
if(CMAKE_BUILD_TYPE STREQUAL "Debug")
    string(REPLACE "-O0 -g3" "-Og -g3" CMAKE_C_FLAGS "${CMAKE_C_FLAGS}")
    string(REPLACE "-O0 -g3" "-Og -g3" CMAKE_ASM_FLAGS "${CMAKE_ASM_FLAGS}")
endif()
```

原因：CubeMX 默认 `-O0`，代码量超过 64KB Flash 时链接失败，`.elf` 不生成，调试器报 “Unable to find executable file”；`-Og` 体积接近 Release，同时保留 `-g3` 源码级调试信息。

`CMakeLists.txt:76-90`：包含用户源文件，并加一个 `size` 自定义目标，每次构建都打印 Flash/RAM 占用（`print_size.cmake`，FLASH 64K / RAM 20K）。

`user_sources.cmake:1-20`：

```cmake
file(GLOB_RECURSE USER_SOURCES
    "${CMAKE_CURRENT_SOURCE_DIR}/Core/Src/*.c"
    "${CMAKE_CURRENT_SOURCE_DIR}/freeRTOS/Src/*.c"
)
list(REMOVE_ITEM USER_SOURCES
    "${CMAKE_CURRENT_SOURCE_DIR}/Core/Src/system_stm32f1xx.c"
)
target_sources(${CMAKE_PROJECT_NAME} PRIVATE ${USER_SOURCES})
target_include_directories(${CMAKE_PROJECT_NAME} PRIVATE
    "${CMAKE_CURRENT_SOURCE_DIR}/Core/Inc"
    "${CMAKE_CURRENT_SOURCE_DIR}/freeRTOS/Inc"
)
```

### 为什么排除 `system_stm32f1xx.c`

CubeMX 生成的 `stm32cubemx` 目标已经编译了一份 `system_stm32f1xx.c`；如果用户目标再 GLOB 进来一份，链接时两个目标都提供 `SystemCoreClock` 等符号 → **multiple definition**。这是 CMake 工程最常见的坑之一。

### GLOB 的缺点

`file(GLOB_RECURSE ...)` 在 **CMake configure 阶段**展开；新增 `.c` 文件后，如果不重新运行 CMake，构建系统不知道新文件存在，会出现“文件明明加了却没编译”。解决：

- 手动重新 configure（删除 `build/CMakeCache.txt` 或执行 `cmake --preset`）；
- 或用 `CONFIGURE_DEPENDS`（CMake 3.12+），但每次构建都会检查目录，略慢。

### 追问与答法

**Q：交叉编译怎么指定工具链？**
用 `-DCMAKE_TOOLCHAIN_FILE=cmake/gcc-arm-none-eabi.cmake`，里面设置 `CMAKE_C_COMPILER=arm-none-eabi-gcc`、`CMAKE_ASM_COMPILER`、`CMAKE_SIZE`、`CMAKE_OBJCOPY` 等；`CMakePresets.json` 把这条命令固化成 preset。

**Q：`-Og` 和 `-O0` 有什么区别？**
`-O0` 完全不优化，代码量大、调试最直观；`-Og` 做“不破坏调试体验的优化”，体积和速度接近 `-O1`，仍保留变量/行号信息。Flash 紧张时用 `-Og`。

**Q：为什么 `add_subdirectory(cmake/stm32cubemx)`？**
CubeMX 生成的内容单独成一个 target（`stm32cubemx`），顶层只负责 `target_link_libraries(... stm32cubemx)`；CubeMX 重新生成时不会覆盖你手写的顶层逻辑。

**Q：`print_size.cmake` 怎么工作？**
自定义 target `size` 依赖主目标，构建后调用 `${CMAKE_SIZE}`（`arm-none-eabi-size`）读 `.elf`，按 `FLASH_SIZE/RAM_SIZE` 算百分比。`ALL` 目标不比较时间戳，所以零改动也会执行。

### 翻车点

- 新增 `.c` 后没重新 configure，以为“代码没生效”。
- 把 `system_stm32f1xx.c` 重复编译，链接报 multiple definition。
- Debug 用 `-O0` 导致 Flash 超 64KB，`.elf` 不生成。
- 把 HAL 驱动也 GLOB 进用户目标，和 CubeMX 目标重复。

### 30 秒口述骨架

`CubeMX 子目录管 HAL/启动/链接 → 顶层管 project/选项/链接 → user_sources GLOB 应用代码 → 排除 system 文件 → -Og 控体积 → size 目标看占用`

### 工作区补充：更严格的 Core/Src 过滤

`FreertosGUILab/user_sources.cmake:1-45` 比平衡车多做了三件事：

1. **Core/Src 不能全量 GLOB**：CubeMX 已经把 `main.c / stm32f1xx_it.c / hal_msp.c / timebase_tim.c / system_stm32f1xx.c / sysmem.c / syscalls.c` 加进 `stm32cubemx` 目标，用户目标若再收一遍就 multiple definition。它用 `list(FILTER ... EXCLUDE REGEX ...)` 一次性排除这 7 类文件（`:13-16`）。
2. **多目录 GLOB**：`freeRTOS/Src`、`key`、`LCD`、`DmmAndGui` 分别收集，再追加过滤后的 `Core/Src`。
3. **链接外部静态库**：`DRivers/lcd.a`（`:38-41`），以及 `-u _printf_float`（`:44`）强制保留浮点 printf 支持。

对比平衡车只排除一个 `system_stm32f1xx.c`，示波器项目的过滤规则更完整——因为它的 `Core/Src` 里既有 CubeMX 文件，也有自己写的 `app_usart1_dma.c`、`memory_monitor.c`，不能一刀切。

面试追问“GLOB 有什么坑”，可以答三点：新增文件要重新 configure、CubeMX 文件重复编译、静态库/链接选项要显式加。

## L01 grep/awk 定位串口日志

### 一句话答案

先按“字节没进来 / 进来没成行 / CPU 死了或复位”三类分现象，再用 **grep 找行、计数、看上下文**，用 **awk 取列、算时间差、做统计**；不要一上来就全文翻日志。

### 真实日志长什么样

`docs/调试记录_蓝牙USART3接收与爆栈复位.md:64-77`：

```
14:13:11.576  B1
14:13:11.679  12345abcdef6789AB2
14:13:11.680  Memory Monitor
14:13:11.717  RC<- [mmove 0 0]
14:13:12.201  B1
```

- `B1` 是 `main()` 里的开机路标；它**重复出现 = 板子在反复复位**。
- 相邻 `B1` 时间差 ≈ 0.41s 就是 IWDG 超时；更长则加上“等第一条指令”的时间。

### grep：找行、计数、上下文

> **前提**：`uart.log` 是串口助手把接收窗口保存下来的文本文件；`grep` 只搜“已经打印出来并落盘”的字符，**不读 MCU 内存**。
> 保存方式：XCOM/SSCOM 勾选“保存接收数据到文件”；MobaXterm 右键会话 → Log to file；保存下来的文件才是 `uart.log`。
> 下面第 3 条里的 `StackOverflow` 只有在固件真的把这个词打印出来时才搜得到。本项目的爆栈钩子（`main.c:769-783`）只写全局变量 `g_ulStackOverflowCount` + 关中断死循环，**不打印**，所以实际日志里不会有这个词；能搜到的是 `B1` 周期重复（复位路标）。爆栈计数只能在调试器 Watch 里看，或者改造钩子让它可输出（见 D01/D03 的补充）。

```bash
# 1. 数复位次数（B1 出现几次就是重启几次）
grep -c "^.*B1$" uart.log

# 2. 看每次 B1 前后 3 行，确认是不是完整开机序列
grep -n -A3 -B3 "B1" uart.log

# 3. 同时找多个关键字（复位/调度器启动失败/爆栈）
grep -nE "B1|SCHED-FAIL|StackOverflow|RC<-" uart.log

# 4. 只看包含时间戳且含 B1 的行
grep -nE "^[0-9]{2}:[0-9]{2}:[0-9]{2}\.[0-9]{3}.*B1" uart.log

# 5. 反向过滤：排除正常行，只看异常
grep -vE "Memory Monitor|Heap:|Task Stacks|=====" uart.log
```

### awk：取列、算时间差、统计

日志第一列是 `HH:MM:SS.mmm`，第二列是内容。把时间转成毫秒并打印相邻 `B1` 间隔：

```bash
awk '
function to_ms(t,   a,b,c) {
    split(t, a, ":")
    split(a[3], b, ".")
    return (a[1]*3600 + a[2]*60 + b[1])*1000 + b[2]
}
$2 == "B1" {
    if (last != "") printf "gap = %d ms\n", to_ms($1) - last
    last = to_ms($1)
}
' uart.log
```

统计每个任务/关键字出现次数：

```bash
awk '{ count[$2]++ }
     END { for (k in count) printf "%-20s %d\n", k, count[k] }
' uart.log | sort -nr -k2
```

只看 `RC<-` 帧并去掉前缀：

```bash
awk -F'RC<- ' '/RC<-/ { print $2 }' uart.log
```

### 按现象选命令（排查方法论）

| 现象 | 先用什么 | 判断 |
|---|---|---|
| 完全没输出 | `grep -c "B1"` | 0 = 没启动/串口线/波特率；>1 = 在复位 |
| 有字节但没成帧 | `grep -c "RC<-"` + `testRcrEecip` | 字节进来但没 IDLE/没成行 |
| 成帧但内容乱 | `awk -F'RC<- '` 看帧内容 | 中断屏蔽窗口丢字节（如 `mmove`） |
| 周期性重启 | `grep -c "B1"` + awk 算间隔 | 间隔 ≈0.41s → IWDG；≈0.5s → 等指令 |
| 某任务没运行 | `grep "任务名"` + 高水位 | 任务没创建/优先级被饿死/栈爆 |

### PowerShell 等价命令（Windows 本地）

```powershell
# 计数
(Select-String -Path .\uart.log -Pattern '^.*B1$').Count

# 看上下文
Select-String -Path .\uart.log -Pattern 'B1' -Context 3,3

# 取 RC<- 后面的内容
Select-String -Path .\uart.log -Pattern 'RC<- \[(.*)\]' |
    ForEach-Object { $_.Matches[0].Groups[1].Value }
```

### 追问与答法

**Q：日志几十 MB，`grep` 会不会很慢？**
grep 是流式扫描，通常够快；更大用 `rg`（ripgrep）或先 `tail -n 100000` 截取最近一段。真正慢的是“把整个文件读进编辑器”。

**Q：时间戳格式不统一怎么办？**
先用 `awk` 统一成毫秒再算差；或者让固件统一输出“上电毫秒数”（如 `HAL_GetTick()`），比 `HH:MM:SS.mmm` 更好算。

**Q：怎么从日志定位到代码？**
关键字（`B1`、`RC<-`、`Memory Monitor`）在代码里 `grep -rn "RC<-" Core/Src` 找到打印点，再结合时间戳倒推执行路径。

**Q：为什么要先分类？**
“串口收不到”至少有三种完全不同的原因（字节没进来/没成行/CPU 死了），用错命令会白查。先看 `B1` 是否重复，能一秒区分“接收 bug”和“复位循环”——这是那次调试最值钱的一步。

### 翻车点

- 一上来 `cat` 整个日志，靠眼睛找。
- 只搜关键字不看上下文，把“正常开机 B1”当成“复位”。
- 时间差用字符串直接相减，不转毫秒。
- 忘了日志时间戳是串口助手加的，不是 MCU 自己打的（换工具就变格式）。

### 30 秒口述骨架

`先分类 → grep -c 计数 → -A/-B 看上下文 → awk 取列算时间差 → B1 重复=复位 → 0.41s=IWDG`
