## 1. 内存监控（`Core/Src/memory_monitor.c`）

### 改前

- 第 7 行 `#include <sys/_types.h>`：这是 newlib 的**内部头文件**，不属于 C 标准库稳定接口。
  本文件其实只用到 `size_t`，直接依赖它属于"能编过但不可移植"的写法（换 ARMCLANG / picolibc 就可能找不到）。
- `vRegisterTaskForMonitoring(TaskHandle_t)`：传 `NULL` 也照单全收，直到打印时才输出
  `[Invalid handle]`，等于静默失效；同一句柄重复注册还会白占槽位（槽位只有 10 个）。
- 打印只有"剩余字数"，没有"申请了多少"，看不出离溢出还有多远，也没有任何告警线。

### 改后

- `<sys/_types.h>` → `<stddef.h>`。
- 注册时：`NULL` 当场拒绝并打印告警；重复句柄直接忽略；槽位耗尽时打印被跳过的任务名。
- 注册接口增加 `uxStackSizeWords`（申请栈深度，单位字）：
  FreeRTOS 的 high water mark 只回答"还剩多少"，不回答"原本给了多少"，
  没有申请值就算不出剩余百分比。
- 输出格式改为：`free 剩余/申请 w (字节), 百分比%`，低于 `MONITOR_LOW_STACK_PERCENT`(20%)
  追加 `<-- 余量偏低，考虑扩栈`。
- 监控任务把自己的栈也纳入打印（否则监控自身爆栈时没人知道）。

### 现在能看到哪些任务（7 个 + 自身）

| 串口显示名 | 申请栈（字/字节） | 职责 |
| --- | --- | --- |
| `led1` | 128 / 512 B | LED 闪烁 |
| `LCD` | 256 / 1024 B | 屏幕刷新（最重的显示任务） |
| `UART1_TX` | 256 / 1024 B | 串口 DMA 发送守门员 |
| `KEYINITSCAN` | 128 / 512 B | 6 个按键扫描 + 各键初始化 |
| `KEYIWORK` | 128 / 512 B | 公共按键队列消费者 |
| `KEYUTASK` | 128 / 512 B | KEYU 专职执行任务（本次新增） |
| `float_archIT` | 128 / 512 B | 每帧 1024 点浮点换算（最重的业务任务） |
| `MemMon` | 256 / 1024 B | 监控任务自身 |

## 2. 任务注册（`Core/Src/main.c`、`DmmAndGui/waveFormCapture.*`）

- `waveFormCapture.c` 增加 `xWaveCaptureGetTaskHandle()`，把私有的 `XFloat_ari_t` 交出去；

## 3. temTest 清理

证据（两条都成立才删）：

1. **不参与编译**：`user_sources.cmake` 的 `GLOB_RECURSE` 只收集
   `Core/Src`、`freeRTOS/Src`、`key`、`LCD`、`DmmAndGui` 五个目录，`temp/` 不在其中。
2. **不被调度**：全仓库检索 `vTempTest_Init` / `vTempPro`，除 `temp/temTest.c`、`temp/temTest.h`
   自身外没有任何调用点；初始化函数从未被调用，任务和定时器都不会创建。

额外理由：该文件仍使用旧版单参数 `vRegisterTaskForMonitoring(XtemP_t)`，
一旦有人把 `temp/` 加进 GLOB 会直接编译失败，属于埋着的雷，故整目录删除。

## 4. KEYU 信号量路

### 改前

- `keyUInit()` 里创建信号量、`rounte = ROUTE_SEM` 等代码被注释，`KeyU.xSem = NULL`；
- `key.c` 的路由又停留在 `ROUTE_QUEUE`，于是 `vkeyOneSca()` 只会走队列分支，
  `else xSemaphoreGive(key->xSem)` 这一支是死代码；
- `vKeyUTask` 被整段注释，**没有任何任务在等这个信号量**。
- 结论：既不是"中断里没释放"，也不是"任务里没有等待点"这么单一——
  是"信号量没创建 + 路由没切 + 没有等待任务"三处同时断。

### 改后（触发链）

```text
[KEYINITSCAN 任务] VkeyTotalInit → keyUInit()：xSemaphoreCreateCounting(4,0)
                                                    KeyU.rounte = ROUTE_SEM
                                                    KeyU.xSem   = xKeyUSem
        ↓ 每 10 ms
vKeyWOrksScan → keyUScan() → vkeyOneSca() 检测 PC13 下降沿
        ↓ rounte != ROUTE_QUEUE
xSemaphoreGive(xKeyUSem)  ← 上限 4，连按 4 次以内不丢，满了也不阻塞扫描任务
        ↓
[KEYUTASK 任务] xSemaphoreTake(portMAX_DELAY) → keyUCallback()
        ↓
vadjust_general_panel / vadjust_RUN_mode_panel / vadjust_SCALE_panel / AdjustCursorPanel
```

- 为什么单独开任务而不是复用公共队列：`keyUCallback` 里会改参数并让信号发生器重算波形，
  属于慢回调；和 KEY1~KEY4、KEYD 共用容量 10 的队列会被它堵住。
- `vKeyUTask` 中保留 `xKeyUSem == NULL` 的兜底分支：信号量在扫描任务里创建，
  若调度顺序变化或创建失败，不至于对空句柄调 `xSemaphoreTake`。

## 5. 构建与占用

- 构建方式：`cmake --build build/Debug --clean-first`（arm-none-eabi-gcc 15.3.1）
- 结果：**0 error**，仅 1 条既有链接告警 `LOAD segment with RWX permissions`（与本次改动无关）

```text
Memory region         Used Size  Region Size  %age Used
             RAM:       47400 B        48 KB     96.44%
           FLASH:       99608 B       256 KB     38.00%
```

- FreeRTOS 堆静态预算（按申请值累加，供参考）：任务栈 8×~0.5~1 KB ≈ 5.6 KB，
  加上 IDLE(128w)/Timer(128w) 两个系统任务约 1.0 KB，再加 TCB×10、队列 4 个、
  软件定时器 2 个与堆块头开销，合计约 8.5~9 KB，`configTOTAL_HEAP_SIZE = 20240` 余量充足。
- 任务栈余量（high water mark）是**运行期数据**，静态分析无法给出，需上板看串口输出（见 §6）。

## 6. 上板验证清单

1. 上电后串口应每 2 s 打印一次 Memory Monitor 区块，8 个任务名齐全、无
   `[Invalid handle]`、无 `Warning: Cannot register more tasks`。
2. 观察 `float_archIT` 的剩余百分比：若低于 20%，把 `WAVE_CAPTURE_TASK_STACK_WORDS`
   从 128 提到 192/256，重建后再看。
3. 按一下 KEYU（PC13）：面板应发生一次可见变化；按住不放只应触发一次（边沿检测）。
4. 快速连按 5 次以上：`xSemaphoreGive` 允许缓冲 4 次，第 5 次丢弃属预期，不应出现卡死/重启。
5. 长时间运行（≥10 min）看掉电前 `Min ever` 是否持续走低（走低说明有泄漏路径）。

## 7. 残留风险

- `key.c` 的 `xSemaphoreGive` 分支没有做 `xSem == NULL` 判断；目前只有 KEYU 走该分支且一定已初始化。
  本次刻意没有改 `key.c`（超出四项范围）。
- 任务注册槽位只有 10 个，再加任务需同步调 `MAX_MONITORED_TASKS`。
- `main.c` / `waveFormCapture.c` 中还含有本次任务开始前就存在的未提交改动，已随对应文件一并提交。
- 运行期栈余量、KEYU 实按效果仍需上板确认。
