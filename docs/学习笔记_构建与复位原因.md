# 学习笔记：构建链路（clone 即可构建、用户源码接入）与复位原因

> 对应 [env.md](env.md) 里的两句话：
>
> 1. 「`Debug` 预设使用仓库自带的 `cmake/gcc-arm-none-eabi.cmake` 和 `third_party/stm32cube_f1`，新机器不用另外安装 STM32CubeF1。」
> 2. 「固件读取后会清除标志位，因此不会把上一次的复位原因误报为本次。」
>
> 这篇笔记回答：**这些机制分别靠什么实现、代码在哪、怎么自己验证。** 共三部分：
>
> 1. 构建为什么与 CubeMX 解耦（预设 + 工具链文件 + 仓库内 HAL）
> 2. `user_sources.cmake` 如何把用户自己写的代码接进构建
> 3. 复位原因码怎么产生，为什么不会把上一次的原因误报成这一次

## 第一部分：构建为什么不依赖 CubeMX

先给结论：CubeMX 在这个项目里只是「生成初始化代码的工具」，**不是构建依赖**。构建链路上真正需要的只有三样东西：

```
cmake --preset Debug
      │
      ├─ 1. 预设：固定生成器 Ninja + 构建目录 + 工具链文件   (CMakePresets.json)
      ├─ 2. 工具链文件：规定交叉编译器、CPU、链接脚本        (cmake/gcc-arm-none-eabi.cmake)
      └─ 3. HAL/CMSIS 源码：已经在仓库里，用相对路径引用     (third_party/stm32cube_f1)
```

本机只需要 `arm-none-eabi-gcc`、`cmake`、`ninja` 在 PATH 里（也就是 env.md 清单的前三条），CubeMX 装不装都无所谓。

### 1.1 入口：CMakePresets.json 把「三条命令的参数」固化成一个名字

[CMakePresets.json](../CMakePresets.json) 里有一个隐藏的 `default` 预设：

```json
{
    "name": "default",
    "hidden": true,
    "generator": "Ninja",
    "binaryDir": "${sourceDir}/build/${presetName}",
    "toolchainFile": "${sourceDir}/cmake/gcc-arm-none-eabi.cmake",
    "cacheVariables": {}
}
```

`Debug` 用 `"inherits": "default"` 继承它，只额外设置 `CMAKE_BUILD_TYPE=Debug`。

所以 `cmake --preset Debug` 等价于手工敲：

```powershell
cmake -G Ninja -B build/Debug `
      -DCMAKE_TOOLCHAIN_FILE=<仓库根>/cmake/gcc-arm-none-eabi.cmake `
      -DCMAKE_BUILD_TYPE=Debug
```

三个细节：

- `hidden: true` 表示这个预设只是模板，不能直接 `--preset default`，防止误用。
- `binaryDir` 里用了 `${presetName}`，所以 Debug/Release 各自有独立构建目录，互不覆盖；产物固定落在 `build/Debug/FreertosGUILab.elf`，env.md 里的路径就是这么来的。
- `toolchainFile` 用 `${sourceDir}` 展开成**仓库自身的绝对路径**。这样不需要用户手工传路径，也避免了 env.md FAQ 第 2 条那种「手工传了相对路径导致找不到工具链文件」的坑。

### 1.2 核心约定：工具链文件只假设「编译器在 PATH」

[gcc-arm-none-eabi.cmake](../cmake/gcc-arm-none-eabi.cmake) 承担了交叉编译的全部约定。按「语句 → 作用 → 少了会怎样」来记：

| 语句 | 作用 | 删掉/写错的后果 |
|---|---|---|
| `set(CMAKE_SYSTEM_NAME Generic)` | 声明目标没有 Windows/Linux 那套主机系统 ABI（裸机/RTOS） | CMake 按 Windows 主机规则生成，行为完全不对 |
| `set(CMAKE_C_COMPILER_FORCED TRUE)` | 跳过 CMake 对编译器的功能探测 | 探测阶段可能报错中断配置 |
| `set(TOOLCHAIN_PREFIX arm-none-eabi-)` + 各编译器 | 指定交叉编译器 | 退化成主机 `gcc`，产出 x86 程序 |
| `set(CMAKE_TRY_COMPILE_TARGET_TYPE STATIC_LIBRARY)` | 编译器自检只「编译」不「链接」 | 裸机没有默认启动文件/libc，自检链接必失败 |
| `set(TARGET_FLAGS "-mcpu=cortex-m3")` | 指定 Cortex-M3 指令集 | 生成 M3 不支持的指令 |
| `-T stm32f103rctx_flash.ld` | 指定链接脚本（FLASH/RAM 布局） | 链接器不知道内存从哪开始 |
| `--specs=nano.specs` | 用 newlib-nano 精简 C 库 | 代码体积暴涨，可能放不进 256 KB |
| `-ffunction-sections -fdata-sections` + `-Wl,--gc-sections` | 每个函数单独成段，链接时丢掉没用的 | Flash 浪费，占用统计失真 |
| `-Wl,--print-memory-usage` | 链接后打印 FLASH/RAM 用量 | env.md 里 `FLASH 99968 B / RAM 44584 B` 就打印不出来 |
| `-Wl,--no-warn-rwx-segments` | 关掉 ld 2.39+ 对裸机链接脚本的 RWX 段警告 | 冷构建无法保证 `0 warning` |

链接标志最后一行 `CMAKE_CXX_LINK_FLAGS` 把 `libstdc++/libsupc++` 用 `--start-group/--end-group` 包起来，是为了让 C++ 静态库（比如 `DRivers/lcd.a`）的符号解析与库顺序无关。

**关键认知**：这个文件里没有任何一行写死「某台电脑」的路径：唯一的外部假设就是 `arm-none-eabi-*` 在 PATH 里。这就是「换机器只需装工具链」的原因。

#### 那「有 FreeRTOS」为什么还写 Generic？

因为 `CMAKE_SYSTEM_NAME` 描述的是**目标平台的 ABI 环境**，不是字面意义上的「有没有操作系统」：

- `Generic` 的含义是：CMake 不假设目标有 Windows/Linux 那套系统调用、动态库、进程模型。所有代码静态链接成一个 ELF，C 库由交叉工具链的 newlib-nano 提供。
- FreeRTOS 是一个**和你的代码一起编译进同一个 ELF 的内核库**（`freeRTOS/Src/*.c`），它没有向 CMake 暴露任何「系统 ABI」。从 CMake 的视角看，它和 `DRivers/lcd.a` 一样，只是又一份要链接的代码。
- 反过来，如果把这里写成 `CMAKE_SYSTEM_NAME Linux`，CMake 会按 Linux 规则去链接 `-ldl`、`-lpthread`、按动态链接处理，裸机根本没有这些东西，配置或链接就会失败。

所以更准确的说法是：**Generic = 没有主机操作系统的 ABI；FreeRTOS 是被静态链接进来的实时内核，不影响这个判断。**

### 1.3 最关键的一步：HAL/CMSIS 的路径从「本机绝对路径」改成「仓库相对路径」

CubeMX 默认生成的 `cmake/stm32cubemx/CMakeLists.txt` 会写成类似：

```cmake
# CubeMX 默认写法（换机器就断）
set(HAL_ROOT "C:/Users/xxx/STM32Cube/Repository/STM32Cube_FW_F1_V1.8.6/Drivers")
```

这行路径只存在于生成它的那台电脑上，别人 clone 下来必然报「找不到 HAL 头文件」。

本仓库在 [cmake/stm32cubemx/CMakeLists.txt](../cmake/stm32cubemx/CMakeLists.txt) 里改成了：

```cmake
# HAL/CMSIS 已随仓库提供，换机器 clone 后无需安装 STM32CubeF1 包
set(HAL_ROOT ${CMAKE_CURRENT_SOURCE_DIR}/../../third_party/stm32cube_f1)
```

之后所有头文件目录和 HAL 源文件都从 `${HAL_ROOT}` 派生，没有一处再出现绝对路径：

```cmake
set(MX_Include_Dirs
    ${CMAKE_CURRENT_SOURCE_DIR}/../../Core/Inc
    ${HAL_ROOT}/STM32F1xx_HAL_Driver/Inc
    ${HAL_ROOT}/STM32F1xx_HAL_Driver/Inc/Legacy
    ${HAL_ROOT}/CMSIS/Device/ST/STM32F1xx/Include
    ${HAL_ROOT}/CMSIS/Include
)

set(STM32_Drivers_Src
    ${CMAKE_CURRENT_SOURCE_DIR}/../../Core/Src/system_stm32f1xx.c
    ${HAL_ROOT}/STM32F1xx_HAL_Driver/Src/stm32f1xx_hal_gpio_ex.c
    ...
)
```

「仓库里自带 HAL」指的就是下面这棵真实的目录树，clone 完成后本地就有：

```
third_party/stm32cube_f1/
├─ CMSIS/                    # 内核头文件 + 设备头文件（stm32f103xe.h 等）
└─ STM32F1xx_HAL_Driver/
   ├─ Inc/  67 个 .h         # HAL 头文件
   └─ Src/  61 个 .c         # HAL 源文件（本工程按需编译其中 20 个，另加 system_stm32f1xx.c）
```

平时 CubeMX 会把这些文件下载到类似 `Documents/STM32Cube/Repository/STM32Cube_FW_F1_V1.8.6/Drivers` 的位置；本项目把它们复制进了仓库的 `third_party/`，所以 HAL 的来源是**仓库**而不是「本机安装的 STM32CubeF1 包」。

再配合两点事实，整条链路就闭环了：

1. `third_party/stm32cube_f1` 已被 git 跟踪（`git ls-files third_party` 共 156 个文件），clone 下来就带着 HAL/CMSIS。
2. [.gitignore](../.gitignore) 只忽略了 `build/`，没有忽略 `third_party/`，所以它不会「本机能编译、别人 clone 后缺失」。

所以构建过程是：**CMake 读预设 → 读工具链文件 → 在 PATH 找 arm-none-eabi-gcc → 编译仓库里的 third_party + Core + 自己的源码 → 按 stm32f103rctx_flash.ld 链接成 elf**，全程不访问 CubeMX 的安装目录或 Repository。

### 1.4 怎么自己验证「真的不依赖」

env.md 第 6 节的冷构建验证就是专门验证这件事：

```powershell
$tmp = "$env:TEMP\FreertosGUILab_clone"
git clone <repo-url> $tmp
Set-Location $tmp
cmake --preset Debug
cmake --build --preset Debug
```

临时目录里没有 `build/`、没有 `compile_commands.json`、也不指向本机任何 CubeMX 目录；如果仍然 `0 error 0 warning` 并产出 elf，就说明 HAL 确实来自仓库、工具链只依赖 PATH。

### 1.5 把 build/ 删了会怎样？

`build/` 里全是**生成物**：`CMakeCache.txt`、`build.ninja`、`.o`、`.elf`、`.map`、`compile_commands.json`。没有一个文件是源码，所以删掉不会丢任何东西，只是要重新走一遍配置：

```powershell
Remove-Item build -Recurse -Force
cmake --preset Debug          # 第一步：重新配置，重建 build/Debug、读预设和工具链、生成 Ninja 工程
cmake --build --preset Debug  # 第二步：全量编译 + 链接
```

三个要点：

1. **两步都不能省**：`cmake --build --preset Debug` 只是去调用 `build/Debug` 里已经生成好的 Ninja 工程；目录被删后没有 `CMakeCache.txt` / `build.ninja`，它会直接报「找不到构建系统/缓存」而失败，不会自动帮你重新配置。
2. 删掉 build/ 再构建，**等价于 env.md 第 6 节的冷构建**：没有任何历史缓存、没有本机 CubeMX 痕迹，仍然 `0 error 0 warning`，才真正证明依赖都来自仓库 + PATH。
3. 另一种必须删 build/ 的情况：**整个工程文件夹搬家或改路径**。`CMakeCache.txt` 里记着生成时的源码目录绝对路径，旧缓存指向旧路径时 CMake 会报 cache 目录不一致，删掉重新 configure 即可。

另外，`build/` 在 [.gitignore](../.gitignore) 里，所以它从来不会进 git —— 别人 clone 下来本来就没有 build/，每次都是「配置 → 构建」两步。

### 1.6 什么时候还会用到 CubeMX

只有一种情况：**改硬件配置**（引脚、时钟、外设），用 CubeMX 打开 `.ioc` 重新生成代码。

但这会带来一个风险：CubeMX 重新生成 `cmake/stm32cubemx/CMakeLists.txt` 时，可能把 `HAL_ROOT` 又改回本机绝对路径。这正是 env.md FAQ 第 3 条「配置时报 HAL 路径不存在」的成因，处理办法就是把那一行改回 `${HAL_ROOT}`。

一句话记忆：**CubeMX 负责生成代码，CMake 负责构建；仓库里自带 HAL，所以构建不需要 CubeMX。**

## 第二部分：复位原因码 POR/PIN/SOFT/IWDG/WWDG/LPWR 是怎么来的

这条链路分三层：**硬件置位 → 固件翻译 → 读后即清**。

### 2.1 硬件层：RCC_CSR 里的一组「粘滞位」

STM32F1 的 `RCC->CSR` 寄存器里有一组复位标志位（位定义见 [stm32f103xe.h](../third_party/stm32cube_f1/CMSIS/Device/ST/STM32F1xx/Include/stm32f103xe.h) 第 1850 行起）：

| 位 | 宏 | 含义 |
|---|---|---|
| 31 | `RCC_CSR_LPWRRSTF` | 低功耗管理复位 |
| 30 | `RCC_CSR_WWDGRSTF` | 窗口看门狗复位 |
| 29 | `RCC_CSR_IWDGRSTF` | 独立看门狗复位 |
| 28 | `RCC_CSR_SFTRSTF` | 软件复位 |
| 27 | `RCC_CSR_PORRSTF` | 上电/掉电复位 |
| 26 | `RCC_CSR_PINRSTF` | NRST 引脚复位 |
| 24 | `RCC_CSR_RMVF` | 写 1 清除上面所有标志 |

两个性质决定了用法：

1. **粘滞（sticky）**：复位发生时硬件把对应位置 1，之后一直保持，断电才会丢；软件不清，它就永远是 1。
2. **只能整体清**：写 `RMVF=1` 一次性清掉全部复位标志，不能只清某一位。

### 2.2 固件层：读一次寄存器快照，按优先级翻译成字符串

[main.c](../Core/Src/main.c) 第 115–127 行：

```c
static const char *pcResetCause(void)
{
    uint32_t csr = RCC->CSR;
    if (csr & RCC_CSR_IWDGRSTF) return "IWDG";
    if (csr & RCC_CSR_WWDGRSTF) return "WWDG";
    if (csr & RCC_CSR_LPWRRSTF) return "LPWR";
    if (csr & RCC_CSR_SFTRSTF)  return "SOFT";
    if (csr & RCC_CSR_PORRSTF)  return "POR";
    if (csr & RCC_CSR_PINRSTF)  return "PIN";
    return "UNKNOWN";
}
```

三个设计点：

- 先 `uint32_t csr = RCC->CSR;` 取**一次快照**，而不是每个 `if` 都去读寄存器，保证这次判断用的是同一时刻的状态。
- 返回的是字符串常量（存在 Flash 里），所以后面清寄存器不会让结果失效。
- **if 链的顺序就是优先级**，从「最具体」排到「最泛化」，`PIN` 必须放最后。

### 2.3 为什么 PIN 必须放最后（最容易踩的坑）

`PINRSTF` 表示「复位信号作用到了 NRST 引脚」。而在 STM32F1 上，其它复位源（上电、看门狗、软件复位）产生的内部复位**也会经过 NRST 复位逻辑**，所以实际读出来常常是多个位同时为 1：上电后可能 `PORRSTF + PINRSTF` 都为 1；看门狗复位后可能 `IWDGRSTF + PINRSTF` 都为 1。

如果代码把 `PIN` 写在最前面，就会永远输出 `PIN`，看门狗复位永远查不出来。同理 `POR` 也要排在 `PIN` 前面。**这就是这段代码看起来「顺序随意」，实际顺序是正确性的一部分。**

### 2.4 时序层：先读、再清、再打印

[main.c](../Core/Src/main.c) 第 275–282 行：

```c
App_USART1_Init();
/* 启动版本行：上电后串口第一行，先取复位原因再清标志 */
{
    const char *pcReset = pcResetCause();
    __HAL_RCC_CLEAR_RESET_FLAGS();
    App_USART1_Printf("fw ver %s | build %s %s | reset %s\r\n",
                      FW_VERSION, __DATE__, __TIME__, pcReset);
}
```

执行顺序和理由：

```
上电/复位
  │  硬件置位 RCC->CSR 对应 bit
  ▼
串口初始化（先让打印通道可用，否则原因取到了也发不出去）
  ▼
pcResetCause()       ← 1. 读：把原因保存成字符串
  ▼
__HAL_RCC_CLEAR_RESET_FLAGS()  ← 2. 清：写 RMVF，把这些粘滞标志归零
  ▼
打印版本行           ← 3. 用已经保存好的字符串，不再依赖寄存器
```

`__HAL_RCC_CLEAR_RESET_FLAGS()` 的实现只有一句：通过位带别名把 `RCC_CSR_RMVF` 写 1（见 [stm32f1xx_hal_rcc.h](../third_party/stm32cube_f1/STM32F1xx_HAL_Driver/Inc/stm32f1xx_hal_rcc.h) 第 1104 行）。

### 2.5 为什么「不清就会误报」——一个具体例子

假设第一次复位是看门狗咬的，`IWDGRSTF=1`。如果没有清标志：

1. 用户按了一下复位键，`PINRSTF` 也被置 1；
2. 此时 `RCC->CSR` 里 `IWDGRSTF` 和 `PINRSTF` 同时为 1；
3. `pcResetCause()` 按优先级先命中 `IWDG`，于是打印「reset IWDG」。

但这次真正的原因是按键复位，看门狗是**上一次**的事。清掉之后，下一次复位寄存器里只会留下本次真正触发的那一位，所以每次打印的都是本次复位的原因。

### 2.6 这些原因码在排查时怎么用

| 输出 | 说明 | 排查方向 |
|---|---|---|
| `POR` | 正常上电 | 无异常 |
| `PIN` | NRST 引脚被拉低 | 按了复位键 / 下载器复位 / 复位电路干扰 |
| `SOFT` | 软件复位 | 代码里调了 `NVIC_SystemReset()`，或调试器执行了复位 |
| `IWDG` | 独立看门狗溢出 | 程序跑飞或卡死，某处没喂狗 |
| `WWDG` | 窗口看门狗溢出 | 喂狗时机不对（太早或太晚） |
| `LPWR` | 低功耗管理复位 | 进低功耗流程 / 选项字节相关配置 |
| `UNKNOWN` | 一个标志都没命中 | 寄存器读取异常，先怀疑时钟/调试链路 |

结合本项目的实际例子：`main.c` 第 271–273 行把 `MX_IWDG_Init()` 注释掉了，原因就是「全工程没有喂狗点，0.41 s 复位一次」。如果哪天打开了 IWDG 却没补 `HAL_IWDG_Refresh()`，串口就会反复出现 `reset IWDG` —— 这和 env.md FAQ 最后一条是同一件事。

### 2.7 延伸易错点

- **清标志 ≠ 关看门狗**：`CLEAR_RESET_FLAGS` 只清历史记录；IWDG 一旦启动会继续计数，该喂还得喂。
- **打印窗口很短**：如果复位后立刻又复位，串口可能只输出半行。看到「反复重启 + 半行乱码」时，先看 reset 原因是不是 `IWDG`。
- **`__DATE__` / `__TIME__` 是「编译 main.c 的时刻」**：增量构建没重新编译 main.c 时，版本行的日期时间会是旧的。要绝对准确，应由构建系统传入宏（例如 `-DFW_BUILD_TIME=...`）。
- **调试器 attach 也会改现场**：连接调试器时的复位/暂停可能产生新的 `SOFT`/`PIN` 标志，所以「看复位原因」最好在纯上电场景下观察。

## 第三部分：user_sources.cmake —— 自己写的代码是怎么接进构建的

### 3.0 它在整个构建里的位置

顶层 [CMakeLists.txt](../CMakeLists.txt) 第 68 行只有一句：

```cmake
include(${CMAKE_CURRENT_SOURCE_DIR}/user_sources.cmake)
```

两个关键后果：

- `include()` 是**文本展开**，不是 `add_subdirectory()`。所以 `CMAKE_CURRENT_SOURCE_DIR` 仍然是仓库根，`CMAKE_PROJECT_NAME`（`FreertosGUILab`）和这个可执行目标也都已经在同一作用域里，文件里可以直接引用。
- 分工清晰：`cmake/stm32cubemx/CMakeLists.txt` 负责「CubeMX 生成的文件 + HAL」；`user_sources.cmake` 负责「手写代码 + 头文件路径 + 预编译库」。

### 3.1 第 1 段：GLOB_RECURSE 收四个目录

```cmake
file(GLOB_RECURSE USER_SOURCES
    "${CMAKE_CURRENT_SOURCE_DIR}/freeRTOS/Src/*.c"
     "${CMAKE_CURRENT_SOURCE_DIR}/key/*.c"
    "${CMAKE_CURRENT_SOURCE_DIR}/LCD/*.c"
    "${CMAKE_CURRENT_SOURCE_DIR}/DmmAndGui/*.c"
)
```

实际收到的内容（本项目当前状态）：

| 目录 | .c 数量 | 内容 |
|---|---|---|
| `freeRTOS/Src` | 9 | FreeRTOS 内核（tasks/queue/list/...）+ `heap_4.c` + Cortex-M3 移植层 `port.c` |
| `key` | 8 | `key.c`、`keyTask.c`、KEY1~4/KEYD/KEYU |
| `LCD` | 1 | `LCD_TASK.c` |
| `DmmAndGui` | 12 | 万用表、波形采集/发生、各 UI 面板 |
| `Core/Src`（下一段加入） | 2 | `app_usart1_dma.c`、`memory_monitor.c` |

合计 32 个用户 .c。可以在 `build/Debug/build.ninja` 里核对：主目标共 39 条源文件编译规则 = 32 个用户 .c + CubeMX 负责的 7 个应用文件（含启动汇编）。

两个必须知道的机制：

1. **`GLOB_RECURSE` 会递归子目录**（`GLOB` 只匹配当前层）。以后在 `DmmAndGui/` 下新建子目录，里面的 .c 也会被自动收进来。
2. **GLOB 只在「配置阶段」执行一次**，结果被固化成 `build.ninja` 里的一条条编译规则。本项目现在给两处 GLOB 都加了 `CONFIGURE_DEPENDS`，构建前会自动重扫目录；如果去掉这个关键字，新增/删除 .c 后直接 `cmake --build` 就不会生效。下一小节把这件事拆开讲清楚。

#### 具体机制：GLOB 在「配置阶段」一次成像

CMake 构建分两个阶段，GLOB 只活在第一个阶段：

| 阶段 | 命令 | 执行者 | 它看到的世界 | 产物 |
|---|---|---|---|---|
| 配置（configure + generate） | `cmake --preset Debug` | CMake | 逐行执行 CMakeLists；`file(GLOB ...)` **在这一刻扫描磁盘**，把文件名列表存进变量 | `build/Debug/CMakeCache.txt`、`build.ninja`、`compile_commands.json` |
| 构建（build） | `cmake --build --preset Debug` | Ninja | **只读 `build.ninja`**，按里面写死的规则编译、链接；完全不看 CMakeLists，也不看目录里多了什么 | `.o`、`.elf`、`.map` |

配置完成后，源文件列表已经以编译规则的形式固化在 build.ninja 里。例如本项目真实的一条（`LCD_TASK.c`）：

```ninja
build CMakeFiles/FreertosGUILab.dir/LCD/LCD_TASK.c.obj: C_COMPILER__FreertosGUILab_unscanned_Debug C$:/Users/.../LCD/LCD_TASK.c || cmake_object_order_depends_target_FreertosGUILab
```

构建阶段没有任何「去目录里找一下」的动作——这就是新增文件被无视的根本原因。

##### 为什么改 CMakeLists 会自动重新配置，新增 .c 却不会

build.ninja 末尾有一条 `RERUN_CMAKE` 规则。与本工程相关的依赖项（实测）是：

```
CMakeLists.txt
cmake/gcc-arm-none-eabi.cmake
cmake/stm32cubemx/CMakeLists.txt
user_sources.cmake
CMakeCache.txt
```

- 改上面任何一个文件（哪怕只是在 `user_sources.cmake` 里加一行注释），Ninja 都会先自动重跑 CMake → GLOB 重新扫描 → 新文件进入 build.ninja。
- 只新建 `LCD/xxx.c`：没有任何一个「被依赖的文件」发生变化，Ninja 判定无事可做。**目录内容本身不是构建依赖。**

这解释了一个看起来奇怪的现象：想让新文件被发现，除了重跑 configure，**改一下 `user_sources.cmake`（触发自动重配置）也等效**。

加了 `CONFIGURE_DEPENDS` 之后，CMake 会额外生成 `build/Debug/CMakeFiles/VerifyGlobs.cmake`，并在每次构建开头插入一个「校验 glob」步骤（Ninja 输出里的 `[0/N] Re-checking globbed directories...`）。一旦发现目录内容和上次不同，它就自动重跑 CMake —— 相当于把「目录变化」补成了一种构建依赖。

##### 实测：新增文件前后的 build.ninja

用一个临时工程（CMake 4.4 + Ninja）验证：

```
# 1. 基线：src/ 只有 main.c，配置并构建成功
cmake -S . -B build -G Ninja ...
cmake --build build

# 2. 新增 src/extra.c（int extra_func(void){ return 42; }），直接 build
cmake --build build
→ ninja: no work to do.
build.ninja 中 extra.c.obj 规则数：0
build/.../extra.c.obj 是否存在：False

# 3. 重新 configure 再 build
cmake -S . -B build
cmake --build build
build.ninja 中 extra.c.obj 规则数：1
build/.../extra.c.obj 是否存在：True
```

##### 三种典型症状（GLOB 未加 CONFIGURE_DEPENDS 时）

| 操作 | 直接 `cmake --build` 的现象 | 原因 | 处理 |
|---|---|---|---|
| 新增 `LCD/xxx.c`，且代码里已经调用它 | 调用方编译通过，链接报 `undefined reference to 'xxx'` | build.ninja 里没有这个文件 | 重跑 `cmake --preset Debug` |
| 新增 `LCD/xxx.c`，暂时没人调用 | `ninja: no work to do.`，静默忽略 | 同上 | 同上 |
| 删除一个已在列表里的 .c | `ninja: error: '.../xxx.c', needed by '...xxx.c.obj', missing and no known rule to make it` | build.ninja 仍指向旧文件 | 同上 |

##### 本项目现在的做法：CONFIGURE_DEPENDS（实测已生效）

`user_sources.cmake` 的两处 GLOB 都已加上该关键字：

```cmake
file(GLOB_RECURSE USER_SOURCES CONFIGURE_DEPENDS
    ...
)
file(GLOB USER_SOURCES_CORE CONFIGURE_DEPENDS "${CMAKE_CURRENT_SOURCE_DIR}/Core/Src/*.c")
```

实测（本仓库，未手动执行 configure，直接 `cmake --build --preset Debug`）：

```
# 在 LCD/ 下新增 glob_probe_tmp.c 后
[0/2] Re-checking globbed directories...
  +C:/.../LCD/glob_probe_tmp.c
[1/2] Re-running CMake...
[1/5] Building C object CMakeFiles/FreertosGUILab.dir/LCD/glob_probe_tmp.c.obj

# 删除该文件后
[0/2] Re-checking globbed directories...
  -C:/.../LCD/glob_probe_tmp.c
[1/2] Re-running CMake...
```

代价与边界：

- 每次构建都多一次目录扫描（目录大、层级深时变慢）；
- CMake 文档说明它不保证所有生成器都支持（Ninja / Makefiles 可用）；
- 它解决「漏编译」，但不利于把「工程包含哪些文件」显式审查；
- 删除源文件后，旧 `.obj` 会留在 build/ 里成为孤儿文件（不参与链接，无害；想彻底干净可删 build/ 全量重建）。

大工程更常见的做法仍是**显式列出源文件**；本项目是「目录结构稳定 + 用 GLOB 省维护」的权衡。

##### 补充：头文件不受这套机制影响

GLOB 只决定编译哪些 `.c`。新增 `.h` 不需要重新 configure（前提是它所在目录已经在 `target_include_directories` 里）：编译器按 `-I` 找头文件，头文件依赖由 `-MMD` 生成的 `.d` 文件自动跟踪，改 `.h` 会触发相关 `.c` 重编。只有**新增头文件目录**时，才必须改 CMakeLists。

为什么不像很多人想的那样直接 `GLOB_RECURSE **/*.c` 一把梭？因为会把 `third_party` 里的 61 个 HAL 源文件、`Core/Src` 里 CubeMX 负责的 7 个文件全部卷进来，导致重复编译甚至重复定义。CMake 官方也不推荐用 GLOB 收集源文件（无法感知文件增删）；这里用它是「目录结构固定、少维护一份文件清单」的权衡。

### 3.2 第 1.1 段：Core/Src 二次收集 + 排除 7 个文件

```cmake
file(GLOB USER_SOURCES_CORE "${CMAKE_CURRENT_SOURCE_DIR}/Core/Src/*.c")
list(FILTER USER_SOURCES_CORE EXCLUDE REGEX
    "/main\\.c$|/stm32f1xx_it\\.c$|/stm32f1xx_hal_msp\\.c$|/stm32f1xx_hal_timebase_tim\\.c$|/system_stm32f1xx\\.c$|/sysmem\\.c$|/syscalls\\.c$")
list(APPEND USER_SOURCES ${USER_SOURCES_CORE})
```

- `Core/Src` 共有 9 个 .c，排除 7 个后，**实际加入 2 个**：`app_usart1_dma.c`、`memory_monitor.c`。
- 正则拆解：
  - CMake 字符串里的 `\\.` 传给正则引擎后是 `\.`，表示「真正的点号」，不会匹配任意字符；
  - `$` 锚定文件名结尾；
  - 每个分支都以 `/` 开头，靠**路径分隔符**界定文件名，避免误伤 `my_main.c`、`syscalls_helper.c` 这类名字。
- 排除的原因要分两类看：

| 被排除的文件 | 实际由谁编译 | 若被 user_sources 再收一次 |
|---|---|---|
| `main.c`、`stm32f1xx_it.c`、`stm32f1xx_hal_msp.c`、`stm32f1xx_hal_timebase_tim.c`、`sysmem.c`、`syscalls.c` | **同一个目标** `FreertosGUILab`，经 `MX_Application_Src` 加入 | CMake 会先把路径归一化（`cmake/stm32cubemx/../../Core/Src/main.c` → `Core/Src/main.c`）再去重，本机 CMake 4.4 实测只生成一条编译规则。所以这里的排除更多是「显式声明归属」，不依赖去重细节 |
| `system_stm32f1xx.c` | **另一个目标** `STM32_Drivers`（OBJECT 库） | 两个目标各编译一份，链接时两份同名符号 → **multiple definition，必失败** |

第二条有直接证据：`build/Debug/build.ninja` 里它的编译规则是

```
cmake/stm32cubemx/CMakeFiles/STM32_Drivers.dir/__/__/Core/Src/system_stm32f1xx.c.obj
```

也就是说，这个文件归 `STM32_Drivers` 这个 OBJECT 库负责，它的 .o 最终会被链接进可执行文件。再被 glob 一次就是真正的重复定义。

所以这条排除表的本质是一句话：**每个 .c 只能有一个「负责编译它的目标」。**

### 3.3 第 2、3 段：把源码和头文件目录加到目标上

```cmake
target_sources(${CMAKE_PROJECT_NAME} PRIVATE ${USER_SOURCES})

target_include_directories(${CMAKE_PROJECT_NAME} PRIVATE
    "${CMAKE_CURRENT_SOURCE_DIR}/Core/Inc"
    "${CMAKE_CURRENT_SOURCE_DIR}/freeRTOS/Inc"
     "${CMAKE_CURRENT_SOURCE_DIR}/key"
      "${CMAKE_CURRENT_SOURCE_DIR}/LCD"
      "${CMAKE_CURRENT_SOURCE_DIR}/DRivers"
      "${CMAKE_CURRENT_SOURCE_DIR}/DmmAndGui"
)
```

各目录的职责：

| 目录 | 里面的头文件 |
|---|---|
| `Core/Inc` | `main.h`、`stm32f1xx_hal_conf.h`、`stm32f1xx_it.h`、`app_usart1_dma.h`、`memory_monitor.h` |
| `freeRTOS/Inc` | `FreeRTOS.h`、`task.h`、`queue.h`、`semphr.h`、`FreeRTOSConfig.h`、`portmacro.h` 等 |
| `key` | `key.h`、`keyTask.h`、`KEY1~4.h`、`KEYD.h`、`KEYU.h` |
| `LCD` | `LCD_TASK.h` |
| `DRivers` | `lcd.h`、`fp.h`（预编译库配套头文件） |
| `DmmAndGui` | `dmm.h`、`waveFormCapture.h`、`waveform_generator.h`、各面板头文件 |

三个要点：

1. **CMake 不会递归搜索 include 目录**：只把列出的目录直接放进 `-I`，子目录要单独写。漏掉某个目录的典型报错就是 `fatal error: xxx.h: No such file or directory`。
2. `PRIVATE` 表示这些路径只给当前目标用，不会传播给依赖它的目标。这里只有一个可执行目标，写 PRIVATE 是语义最准确的。
3. 用 `target_include_directories` 而不是全局 `include_directories`：作用范围限定在目标上，不会污染其他 target。

### 3.4 第 4 段：链接预编译静态库 lcd.a

```cmake
target_link_directories(${CMAKE_PROJECT_NAME} PRIVATE
    "${CMAKE_CURRENT_SOURCE_DIR}/DRivers"
)

target_link_libraries(${CMAKE_PROJECT_NAME}
    "${CMAKE_CURRENT_SOURCE_DIR}/DRivers/lcd.a"
)
```

- `DRivers/lcd.a` 是一个 **81,594 字节的预编译静态库**（源码不在仓库，只提供 `lcd.a` + 头文件 `lcd.h`/`fp.h`）。静态库在链接时按需抽取成员：只有被引用到的 `.o` 才会进固件。
- `target_link_directories` 相当于给链接器加 `-L` 搜索路径；但下一句链接时用的是**绝对路径**，所以这行对当前写法其实是冗余的（保留无妨；如果以后改成 `-llcd` 的写法才必须要有它）。
- `target_link_libraries` 没写 `PRIVATE/PUBLIC` 的「普通签名」在可执行目标上等价于 PRIVATE，可以工作；新写的代码建议显式写 `PRIVATE`，意图更清楚。

### 3.5 第 5 段：`-u _printf_float` 为什么注释写着「必须保留」

```cmake
target_link_options(${CMAKE_PROJECT_NAME} PRIVATE -u _printf_float)
```

这条要和第一部分的 `--specs=nano.specs` 连起来看：

1. newlib-nano 为了省 Flash，把**浮点格式化代码单独放在一个目标文件里，默认不链接**（静态库的规则：只有符号被引用才抽取对应成员）。
2. `-u _printf_float` 是 GCC 驱动选项，等价于传给链接器 `--undefined=_printf_float`：强行把这个符号标记为「未定义、需要解析」，链接器就会去 `libc_nano.a` 里把浮点格式化实现抽出来。
3. 删掉它的后果：`App_USART1_Printf("%f", ...)` 打印不出正确的小数（通常表现为输出为空或异常字符），因为浮点格式化代码根本没进固件。
4. `target_link_options` 放**链接器选项**，`target_link_libraries` 放**库**，两者不要混用。

### 3.6 一张表记住每段职责

| 段落 | 做什么 | 删掉/改错的后果 |
|---|---|---|
| `GLOB_RECURSE` | 收集 4 个目录的用户 .c | 相关源文件不编译 → `undefined reference` |
| `GLOB` + `FILTER EXCLUDE` | 补收 `Core/Src` 中自己写的 2 个文件，排除 CubeMX 负责的 7 个 | 漏排除 → `system_stm32f1xx.c` 重复定义；过度排除 → 用户文件不编译 |
| `target_sources` | 把源文件挂到可执行目标 | 同上 |
| `target_include_directories` | 给编译器 `-I` 路径 | 头文件找不到，编译失败 |
| `target_link_directories` + `target_link_libraries` | 链接预编译 `lcd.a` | LCD 相关符号 `undefined reference` |
| `-u _printf_float` | 强制链入浮点格式化实现 | `%f` 打印失效 |

### 3.7 易错点清单

- **新增 .c 后忘了重新配置**：只 `cmake --build` 不会重新 GLOB，新文件不参与编译。
- **两个目标编译同一个 .c**：`system_stm32f1xx.c` 就是例子，链接时报 multiple definition。
- **正则写错**：`main.c` 没加 `$` 会连 `main.c.bak` 之类一起排除（更常见的是漏掉 `/` 前缀，误伤名字里带 `main.c` 的文件）。
- **头文件目录漏列**：CMake 不递归，子目录必须单独写。
- **浮点打印突然失效**：先检查 `-u _printf_float` 是否还在（如果同时要用 `scanf` 读浮点，还需要 `-u _scanf_float`）。

## 三句话背下来

- **构建**：预设绑定工具链文件，工具链只假设编译器在 PATH，HAL 以仓库相对路径随 git 提供 —— 所以 clone + 装工具链即可构建，CubeMX 只用来改 `.ioc`。
- **用户源码**：`user_sources.cmake` 用 GLOB 收自己的 4 个目录 + 排除 `Core/Src` 里 CubeMX 负责的 7 个文件，再补 include 路径、链 `lcd.a`、用 `-u _printf_float` 打开浮点打印；原则是「每个 .c 只能有一个编译它的目标」，且 **GLOB 只在配置阶段生效——本项目用 `CONFIGURE_DEPENDS` 让构建前自动重扫，去掉它就必须手动重新 configure**。
- **复位原因**：硬件把复位源写进 `RCC->CSR` 的粘滞位，固件**读一次快照 → 按「具体优先、PIN 最后」翻译 → 立刻清 RMVF**，这样每次打印的都是本次复位原因。
